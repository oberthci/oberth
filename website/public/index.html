PIPELINE / Argo Workflow YAML

Your pipeline is Argo Workflow YAML. Standard, auditable, explicit.

.oberth/build.yaml for branches, .oberth/release.yaml for tags. Standard Argo Workflow resources — DAG tasks, container templates, explicit dependencies. Oberth handles submission, identity, source injection, and the green/red gate. The server never executes repository code.

.oberth/build.yaml excerpt
# Branch-trigger CI pipeline (abbreviated)
apiVersion: argoproj.io/v1alpha1
kind: Workflow
spec:
  entrypoint: ci
  templates:
  - name: ci
    dag:
      tasks:
      - name: setup
        template: setup
      - name: lint
        template: lint
        depends: setup
      - name: test
        template: test
        depends: lint
      - name: build-amd64
        template: build-amd64
        depends: test

  - name: vet
    container:
      image: "golang:1.26-trixie@sha256:..."
      command: ["/tmp/oberth-tools/bin/go"]
      args: ["vet", "./..."]
→Each template is its own container. Every DAG task gets its own exit code, resource limits, and a named log slice you can fetch alone.
→Dependencies are declared, never ambient. No workflow may rely on a tool merely existing in the base image. Tools are fetched, pinned and unpacked by inline setup steps — each fetch with its own SHA-256 check and named verdict.
→Caches accelerate, they don't decide. Persistent Go caches are split by repository and trust tier — a poisoned branch build can't feed bytes into a signed release artifact.
→Identity is enforced server-side. Oberth forces the ServiceAccount by trigger tier — branch Workflows get only approved upstream-scoped secrets, release Workflows get the release identity. The YAML cannot override it.

No rate limits. No 429s.

Oberth processes git operations in-process and submits Argo Workflows directly via the Kubernetes API. No upstream API quota between an agent and its CI. The queue is yours: a concurrency knob, FIFO for the rest, and supersession so a rebase-happy agent cancels its own stale runs instead of stacking them.

AGENTS / MCP interface

Eighteen tools. Zero babysitting.

Agents lose SHAs to context compaction — so status takes a branch. Agents can't sleep-poll politely — so wait long-polls to a terminal state and returns a clean still running at the timeout. The failure that would be lost when an agent is reaped becomes an issue another agent can lock and fix. Secret access approval is managed through access_allow, access_revoke, and access_list — the same interface agents already use for everything else.

statusCI state for branch, short or full SHA — failed step, issue, run states
logsexactly one named-step log slice — no verbose dumps
waitlong-poll to terminal state; clean still_running at timeout, call again
run_getfull run metadata — steps, timing, exit codes, linked issues
run_logsstructured log output for a complete run, all steps
syncpark the WIP branch upstream without a green gate — even red
promotegreen-gate → local merge → CI on merged tree → non-forced push · returns ID
promote_statuswait semantics on the append-only promotion record
access_listshow all secret access grants for a repo — which step can reach which secret
access_allowgrant a repo+step access to a named secret — ConfigMap-driven, fail-closed
access_revokerevoke a secret access grant — takes effect on the next run
issue_create / get / updateplain records, no format ceremony
issue_close / delete / listclose keeps history; delete is for mistakes; list pages by 50
issue_lock5-min TTL lock owned by your uplink, renews while you work it

TRUST / The release boundary

The trigger is the security boundary.

The visibility boundary is intentional and explicit. One rule decides everything: a branch push is a CI workflow and receives only approved upstream-scoped secrets. A tag push is a release workflow and receives exactly the credentials your repository declares. Release credentials are never reachable from a branch pipeline. Oberth forces the identity by trigger tier; the YAML cannot override it.

three pushes · one rule
$ git push oberth feat/rotate-keys
  trigger: branch → CI run
  secrets: approved upstream-scoped only · release credentials unreachable · non-root
$ git push oberth v0.13.22
  gate: commit reachable from default branch ✓ · merge-base --is-ancestor
  trigger: tag → release run
  secrets: r2-publisher, cosign-key ← declared ∩ allowlist, fetched from OpenBao in-pod
  delivery: memory-only via tmpfs · log values masked automatically
$ git push oberth v9.9.9 # tag on an un-promoted sha
  gate: not reachable from default branch → rejected · nothing runs, nothing mounts
!Red never leaves the box. Branch builds stay local until an agent fixes them. Release credentials exist only in pod memory, masked before storage. The only path to your upstream forge is a green gate.
declared, staticallyThe server reads the declared secret paths from the release Workflow YAML without executing repository code. Oberth fetches each path from the secret store at release admission with its own ServiceAccount identity.
memory-only deliveryValues are injected over the Kubernetes exec stream into a memory-backed volume — tmpfs, 0400, never etcd, never node disk. Every value is masked in the live log stream before a byte reaches storage.
automatic log maskingCredentialed step logs are automatically masked. Words and numbers remain readable; tokens, keys, and encoded values are replaced. You see what happened without seeing what was used to do it.
satellite, not sovereignOberth builds, tests against the real published artifacts, and syncs the proven tag upstream. Your own release pipelines take it from there — Oberth marks the tag complete, it doesn't own your rollout.
TRUST / The audit chain

Tamper-evident against its own host.

Every push, sync, promotion and issue mutation is attributed to a durable uplink and chained. The chain head is then anchored where Oberth — and whoever holds Oberth's disk — cannot rewrite it. Roll back the whole PVC and the system fails closed instead of forgetting.

OUTSIDE THE BOX

→Fail-closed by construction. Before readiness and before every mutation, Oberth verifies the local chain, the signed timestamp, the Rekor history and the external continuity records. A pending intent with no completed witness keeps every mutation gate shut.
→Even bootstrap obeys the gate. In-pod upstream add and uplink add go through the live daemon's same fail-closed mutation gate over a private socket. If the audit proof is unavailable, setup changes nothing.

ALPHA / Straight answers

Before you route a push through anything.

Does Oberth replace GitHub, GitLab, or Codeberg?+
No. Your Git host remains authoritative for pull requests, review, issues, releases and collaboration. Oberth is a satellite CI in front of it — it proves AI-generated code before it reaches upstream, force-syncs green work so nothing lives only on the box, and syncs proven tags so your release pipelines can take over.
How does Oberth run pipelines?+
Each push submits the repository's Argo Workflow YAML (.oberth/build.yaml for branches, .oberth/release.yaml for tags). Oberth sets metadata, forces the ServiceAccount identity by trigger tier, and injects the source checkout. Each DAG task runs in its own pod with its own container image, exit code, and named logs. Pipeline steps run in right-sized containers — golang for Go builds, hashicorp/terraform for IaC, trivy for scanning.
How does secret access approval work?+
Every secret a pipeline step can access must be explicitly approved — per repo, per step, per secret name. Grants are stored in a ConfigMap and the system is fail-closed: if a step requests a secret it has not been granted, the run fails and an issue is filed automatically. Use oberth access allow <repo> <step> <secret> or the MCP tools (access_allow, access_revoke, access_list). Compare to GitHub Actions, where organization secrets are silently available to every workflow in every repo — Oberth makes the grant explicit and auditable.
What runs when a branch is pushed? And a tag?+
Branch push → CI workflow: submits .oberth/build.yaml, FIFO-queued (default 3 concurrent), CI-tier ServiceAccount with only approved upstream-scoped secrets. Release credentials are never reachable. A newer push to the same branch supersedes the run. Tag push → release workflow from .oberth/release.yaml, only if the tag's commit is reachable from the default branch — with the release-tier ServiceAccount that can authenticate to your secret store.
Does an agent need an Oberth SDK?+
No. Standard Git is the base integration. For structured access there's a built-in MCP server with 18 tools — status (by branch, because agents lose SHAs to context compaction), single-step logs, long-poll wait, red-tolerant sync, append-only promote, secret access management, and an issue queue with uplink-owned locks. Claude Code and Codex work out of the box.
What is public and what requires authentication?+
Everything requires authentication. The dashboard, step logs, audit records, MCP and the JSON API all require a bearer token tied to your uplink (stored server-side only as a SHA-256 digest). Git push requires an authorized SSH key. Only /healthz and /readyz are unauthenticated.
Can I deploy my own instance?+
Yes — that's the intended shape. One Helm chart on any Kubernetes, including a single k3s machine — the 187-scenario acceptance matrix runs green on k3s, kind and k0s. State lives on one PVC (SQLite, git cache, logs, workspaces) with a keep policy; identities live in K8s Secrets so pod restarts don't retrain your agents' known_hosts. Oberth is open source (Apache 2.0).

WHY / No access change slips through a git commit

No access change slips through a git commit.

In GitHub Actions, organization secrets are silently available to every workflow in every repo. A new step that references ${{ secrets.PROD_KEY }} gets the value without anyone approving the change. In Oberth, every secret a pipeline step can reach must be explicitly granted — per repo, per step, per secret name. The system is fail-closed: an unapproved access attempt fails the run and files an issue. No secret is reachable without a deliberate oberth access allow.

access approval · the grant that makes it explicit
# A deploy step needs the R2 upload token. Without approval:
$ git push oberth feat/add-deploy-step
  step: deploy FAILED · secret "r2-token" not approved for this repo+step
  issue: #52 filed · unapproved secret access: payments-api / deploy / r2-token
# An administrator approves the grant:
$ oberth access allow payments-api deploy r2-token
  grant: payments-api / deploy / r2-token APPROVED
# Next push succeeds. The grant is stored in a ConfigMap — auditable, versioned.
Per repo + step + secretGrants are scoped to the intersection of repository, pipeline step, and secret name. A step in one repo cannot silently inherit a grant from another repo. Adding a new step that touches a secret requires a deliberate approval — not a YAML edit.
ConfigMap-driven, fail-closedAccess grants are stored in a Kubernetes ConfigMap — declarative, auditable, managed through oberth access allow/revoke or the MCP tools. If a grant is missing, the run fails. If a grant is revoked, the next run fails. There is no fallback.
Auto-issue on unapproved accessWhen a step attempts to access a secret it has not been granted, Oberth files an issue naming the repo, step, and secret. The issue is the approval request — visible, trackable, and closed only when the grant is made or the step is removed.
Compare to GitHub ActionsIn GitHub, organization secrets are available to every workflow in every repo by default. A contributor adds ${{ secrets.PROD_KEY }} to a workflow file, and the value is silently injected. No notification, no approval, no audit trail for the access change itself. Oberth inverts this: the default is denial.
WHY / Per-step credential isolation

Each step gets its own pod. Its own credentials. Its own blast radius.

Oberth runs pipelines as Argo Workflows — one pod per DAG task, not a monolithic container running all steps in sequence. Each step declares its own container image, resource limits, and credential scope. A lint step runs in a linter image with no secrets. A deploy step runs in a deploy image with exactly the credentials it was approved for. A compromised lint step cannot reach the deploy credentials — they exist in a different pod, a different ServiceAccount context.

Right-sized containersPipeline steps run in purpose-built containers — golang for Go builds, hashicorp/terraform for IaC, trivy for scanning. No monolithic runner image carrying every toolchain. Each step declares what it needs.
DAG dependenciesSteps declare their dependencies explicitly. test depends on lint; build depends on test. Independent steps run in parallel. The dependency graph is visible in the Workflow YAML — no implicit ordering from a shared container.
Unprivileged by defaultEvery DAG task runs as user 65534, runAsNonRoot, default seccomp, no privilege escalation, no ServiceAccount token, no docker socket. An unprivileged container per step, not a privileged engine.
WHY / Log masking

See what happened. Not what was used to do it.

Oberth provides a log-redaction helper that credentialed steps can invoke to mask secret values in the log stream. Oberth's own release pipeline uses it. However, log redaction is a repository-invoked step, not an admission-enforced boundary — the server ingests the raw container log stream from Argo and does not automatically register or mask secret values. Pipelines that handle credentials should wrap their steps with the redaction helper or use envconsul's built-in environment injection to avoid printing secrets.

Repository-invokedThe redaction helper is available as a pipeline step. Pipelines that handle secrets should invoke it explicitly; it is not injected automatically by admission.
Server-side log ingestionOberth ingests the raw main-container log stream from Argo. On the current Argo execution path, the server does not see secret values (they are fetched in-pod by envconsul), but it also cannot redact them — redaction is the pipeline's responsibility.
