00 / Why "Oberth"

CI at local speed. Upstream gets only green.

Every agent push runs full CI on your own box — no forge queue, no rate limits, feedback in seconds. Green work syncs upstream automatically. Red work never leaves the box: it becomes an issue, gets fixed, and re-runs until it passes. Your forge only ever receives code that's already proven. The name? A burn at periapsis — closest approach — buys the most orbit for the least fuel. Same idea: spend the energy at the push.

01 / The control loop

A gate at the one boundary every coding agent already understands.

No editor plugin, no SDK. A push enters Oberth through standard Git, gets a run in one Kubernetes Job, and moves upstream only when it's green. When it isn't — the failure becomes an issue an agent can pick up.

iYour forge remains the source of truth. Oberth is a satellite CI and quality gate — not a replacement for pull requests, review, issue tracking, or your release governance. Green work is force-synced to your forge; nothing lives only on the box.

PIPELINE / periapsis.go

Your pipeline is a Go file. Run it locally first.

.oberth/periapsis.go is what a workflow YAML always wanted to be: named burns and steps with real exit codes and named log capture — in a language your agents already write, executable on a laptop before it's pushed. yaegi interprets it inside the Job; the server never evaluates repository code.

.oberth/periapsis.go excerpt
// release burns get exactly these — nothing else, ever.
var ReleaseSecrets = []string{"r2-publisher", "cosign-key"}

func Pipeline(p *periapsis.P) {
  setup := p.Burn("setup")
  setup.Step("toolchain",        // pinned + checksummed
    "./tools/install.sh go1.24.5 golangci-lint trivy")

  ci := p.Burn("ci", setup)
  ci.Step("lint",  "golangci-lint run ./...")
  ci.Step("test",  "go test -race ./...").Timeout(45*time.Minute)
  ci.Step("build", "go build ./cmd/...")

  rel := p.ReleaseBurn("release", ci)  // tag-trigger only
  rel.Step("publish", "./tools/publish.sh")
}
→Steps are subprocesses, not containers. One Job, one container; each step gets its own process group, exit code, bounded timeout (30 min default, overridable) and a named log slice you can fetch alone.
→Dependencies are declared, never ambient. No workflow may rely on a tool merely existing in the runner image. Setup steps install pinned versions with SHA-256 checks; the runner resolves commands from the merged step PATH, never its own.
→Caches accelerate, they don't decide. Persistent Go caches are split by repository and trust tier — a poisoned branch build can't feed bytes into a signed release artifact.
→A hung step can't wedge the queue. Timed-out steps have their whole process group killed and joined; the outer Job deadline defaults to 12 hours; logs cap at 64 MiB with per-step byte ranges that survive pod reaping.
λWhy not Argo? Earlier alphas dispatched Argo Workflows. The rewrite runs one plain Kubernetes Job per push — no CRDs, no controllers, no step containers. Multi-container orchestration was a road that ends with rebuilding Argo; we turned around.

No rate limits. No 429s.

Oberth processes git operations in-process and creates Jobs directly via the Kubernetes API. No forge API quota between an agent and its CI. The queue is yours: a concurrency knob, FIFO for the rest, and supersession so a rebase-happy agent cancels its own stale runs instead of stacking them.

AGENTS / MCP interface

Thirteen tools. Zero babysitting.

Agents lose SHAs to context compaction — so status takes a branch. Agents can't sleep-poll politely — so wait long-polls to a terminal state and returns a clean still running at the timeout. The failure that would be lost when an agent is reaped becomes an issue another agent can lock and fix.

statusCI state for branch, short or full SHA — failed step, issue, burn states
logsexactly one named-step log slice — no verbose dumps
waitlong-poll to terminal state; clean still_running at timeout, call again
syncpark the WIP branch upstream without a green gate — even red
promotegreen-gate → local merge → CI on merged tree → non-forced push · returns ID
promote_statuswait semantics on the append-only promotion record
issue_create / get / updateplain records, no format ceremony
issue_close / delete / listclose keeps history; delete is for mistakes; list pages by 50
issue_lock5-min TTL lock owned by your uplink, renews while you work it

TRUST / The release boundary

The trigger is the security boundary.

One rule decides everything: a branch push is a CI burn and mounts nothing. A tag push is a release burn and mounts exactly the secrets your repository names — intersected with the administrator allowlist. Oberth mounts, periapsis.go names, nothing else changes.

three pushes · one rule
$ git push oberth feat/rotate-keys
  trigger: branch → CI burn
  secrets mounted: none · no SA token · non-root · that's the whole story
$ git push oberth v0.11.0
  gate: commit reachable from default branch ✓ · merge-base --is-ancestor
  trigger: tag → release burn
  secrets mounted: r2-publisher, cosign-key ← ReleaseSecrets ∩ allowlist, nothing else
  logs: every mounted value registered with the redactor before disk or API
$ git push oberth v9.9.9 # tag on an un-promoted sha
  gate: not reachable from default branch → no burn · nothing runs, nothing mounts
declared, staticallyThe server parses the literal var ReleaseSecrets = []string{…} from periapsis.go without executing repository code. An undeclared credential is never mounted; a requested-but-unapproved name fails admission.
snapshotted, immutableSecret bytes are copied into a Job-owned snapshot Secret so values can't change mid-release, projected read-only at /secrets/<name>/<key>.
satellite, not sovereignOberth builds, tests against the real published artifacts, and syncs the proven tag upstream. Your own release pipelines take it from there — Oberth marks the tag complete, it doesn't own your rollout.
TRUST / The audit chain

Tamper-evident against its own host.

Every push, sync, promotion and issue mutation is attributed to a durable uplink and chained. The chain head is then anchored where Oberth — and whoever holds Oberth's disk — cannot rewrite it. Roll back the whole PVC and the system fails closed instead of forgetting.

SQLite audit rows
gap-free SHA-256 chain · actor on every mutation
ON THE PVC
RFC 3161 timestamp
independent TSA (Sectigo) signs each chain head over HTTPS
OUTSIDE THE BOX
Rekor witness
signed heads published to the public transparency log under a stable witness identity
PUBLIC
Immutable K8s records
intent/completion objects Oberth can create, get, list — never update, patch or delete
ROLLBACK-EXTERNAL
→Fail-closed by construction. Before readiness and before every mutation, Oberth verifies the local chain, the signed timestamp, the Rekor history and the external continuity records. A pending intent with no completed witness keeps every mutation gate shut.
→Even bootstrap obeys the gate. In-pod upstream add and uplink add go through the live daemon's same fail-closed mutation gate over a private socket. If the audit proof is unavailable, setup changes nothing.

—No issue sync. SQLite issues are the ephemeral CI work queue; your forge stays the tracker of record. They never pretend otherwise.

ALPHA / Straight answers

Before you route a push through anything.

Does Oberth replace GitHub, GitLab, or Codeberg?+
No. Your forge remains authoritative for pull requests, review, issues, releases and collaboration. Oberth is a satellite CI in front of it — it proves AI-generated code before it reaches the forge, force-syncs green work so nothing lives only on the box, and syncs proven tags so your release pipelines can take over.
What happened to Argo Workflows?+
Retired in the rewrite. Every run is now one plain Kubernetes Job — single container, no CRDs, no controllers, no init-container step chains. The pipeline is .oberth/periapsis.go, interpreted by yaegi inside the Job pod; steps run as subprocesses with per-step exit codes and named logs. Multi-container orchestration is a road that ends with rebuilding Argo, so we don't walk it.
What runs when a branch is pushed? And a tag?+
Branch push → CI burn: one Job, FIFO-queued (default 3 concurrent), zero secrets, no ServiceAccount token, non-root, resource-limited. A newer push to the same branch supersedes the run. Tag push → release burn, only if the tag's commit is reachable from the default branch — with exactly the secrets your repo's literal ReleaseSecrets declares, intersected with the admin allowlist, snapshotted and masked in logs.
Does an agent need an Oberth SDK?+
No. Standard Git is the base integration. For structured access there's a built-in MCP server with 13 tools — status (by branch, because agents lose SHAs to context compaction), single-step logs, long-poll wait, red-tolerant sync, append-only promote, and an issue queue with uplink-owned locks. Claude Code and Codex work out of the box.
What is public and what requires authentication?+
Status pages at oberth.ci — runs, repos, issues, upstream/cluster status — are public. Step logs, audit records, MCP and the JSON API require a bearer token tied to your uplink (stored server-side only as a SHA-256 digest). Git push requires an authorized SSH key. The visibility boundary is intentional and explicit.
Can I deploy my own instance?+
Yes — that's the intended shape. One Helm chart on any Kubernetes, including a single k3s machine. State lives on one PVC (SQLite, git cache, logs, workspaces) with a keep policy; identities live in K8s Secrets so pod restarts don't retrain your agents' known_hosts. No external dependencies — not even Argo. Oberth is proprietary, currently offered through the alpha pilot.
