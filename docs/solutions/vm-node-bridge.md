# Privileged node bridge for the Beacon pilot

The Beacon pilot remains inactive. This source adds a narrow node-local route for exact conductor attachment, but no chart installation, Service, scheduler provider or credential is enabled. The existing Kubernetes Pod-name attach route does not bind the runtime container chosen after name resolution. The bridge holds a CRI socket on the target node and serves one fixed attach endpoint over HTTP/2 mutual TLS. It is a trusted recipient of the synthetic fixture plaintext it proxies.

Oberth first observes and journals the admitted Job, sole Pod UID, actual conductor container, image, spec, node and Kubernetes start. The journal spends a separate one-use attach claim before opening a node channel. A failure, timeout, lost response or bridge restart never regrants that claim. The client sends the sealed plan, attempt, claim and immutable admission time; it never sends a command, runtime URL or candidate-supplied selector. The node agent checks the dedicated client certificate URI, its own node name, deadline, exact full 64-hex containerd ID, CRI running status, image digest, nanosecond start, exact container inventory and sandbox Pod UID/name/namespace. It asks CRI to attach that same ID and rechecks before consuming the transient URL.

The CRI URL is accepted only under the operator-pinned local `https://` origin and CA with no proxy, redirect or alternate path. The URL token remains inside the node process and is never logged. The node endpoint uses a node-specific server certificate and a separate Oberth client identity. Node key, client CA, streaming CA, CRI socket and qualification receipt must be operator-installed on the host with protected filesystem custody, outside conductor and candidate Pods. Oberth must likewise receive its client credential through an operator-controlled protected path. No Kubernetes Secret or workload token is defined here.

Before `WithBootstrap` lends fixture capabilities, Oberth sends a fresh, nonsecret `attach-challenge` through the selected stream. The pinned conductor replies with the exact `attach-proof`; Oberth validates its run, plan, attempt, full container ID and nonce, then durably records the CRI nanosecond start without rewriting the Kubernetes second-precision observation. Only then may bootstrap cross the channel. The proof establishes continuity of the selected stream, not process identity on its own. Results still require exact container termination, UID cleanup and the existing finite restart CAS. The node protocol has no exec, logs, port-forward or reconnect operation. Input, output, stderr, frame sizes, deadlines and closure are bounded; a missing authenticated stream trailer fails the result.

Activation requires a reviewed qualification receipt whose exact SHA-256 is passed to the node binary, plus evidence for the **installed** containerd/k3s executable and configuration: no full-ID reuse or task replacement through attach URL consumption, verified HTTPS streaming origin/CA, real half-close/cancellation/copy behavior, and matching CRI image/start semantics. Source inspection and fake CRI tests do not supply this evidence. An operator must provision node-specific identities, key rotation, host socket access and network policy before any live use. Until then, the scheduler and trusted-policy dispatch remain unavailable.
