# Install answers

`oberth setup --answers-out /path/answers.json` exports the reviewed wizard
answers. Add `--dry-mode` to export without installing. The destination must
not exist. The file is mode 0600 and contains configuration, never credentials.

`oberth install --answers /path/answers.yaml` reads YAML or JSON, prints Review,
and refuses changes until the operator passes `--yes`. Obtain explicit consent
to the selected cluster before using that flag. Scalar command-line flags
replace file values; repeated flags append to file lists.

```yaml
version: 1
config:
  ContextName: selected-context
  InstallSecretStore: true
  Namespace: oberth
  ArgoNamespace: oberth-argo
  ArgoParallelism: 4
  ArgoNamespaceParallelism: 0
  ClientHost: localhost
  ClientAccess: none
  ForgeType: github
  ForgeOrg: acme
  UplinkIdentity: admin@workstation
  AdminSSHPublicKeyPath: /path/to/local-key.pub
  SecretsFile: /secure/outside-repository/install.secrets
```

The version 1 `config` object uses the exported field names of
[`installer.Config`](../internal/installer/installer.go). The wizard exporter
writes the complete object; all fields are optional and use the same defaults
as the engine. Unknown or duplicate keys, including nested keys, are refused.
Strings are strings, booleans are booleans, lists contain strings, optional
parallelism values are integers. `ArgoParallelism` sets Argo's native
`controller.parallelism`; `ArgoNamespaceParallelism` sets
`controller.namespaceParallelism`. New releases default to 4 and 0 respectively
without CPU or node calculations. Omit either field to preserve that setting on
an existing Argo release. An explicit 0 means unlimited. Both fields appear in
Review and can be edited there in setup, or overridden with
`--argo-parallelism` and `--argo-namespace-parallelism`.
`Timeout` is an integer number of nanoseconds. `Release` has `Dir`, `Origin`, and
`ChartRepository` strings. Every wizard answer maps to this object. Use file
paths for imported key material and Helm values; never put a credential into
an answers file. `BinaryVersion` is set by the running binary.

`--admin-ssh-public-key file` creates an admin uplink before forge onboarding;
`-` reads the public key from stdin. Generate the key on the client machine.
Only the public half crosses the administration connection. Private keys and
oversized input are refused before installation. `--uplink-identity` names it.

`--secrets-file` reserves a new 0600 file outside a Git worktree and saves each
credential immediately. The `KEY=value` format has `OPENBAO_ROOT_TOKEN`,
`OPENBAO_UNSEAL_KEY`, `OBERTH_UPLINK_TOKEN`, and, when generated by this install,
`OBERTH_UPSTREAM_PRIVATE_KEY_BASE64` (base64 of the OpenSSH private key).
Existing upstream private keys are not exported. The output reports only the
path, count and SHA-256. A failed write makes the install fail. For production
resume or `install --upgrade`, an existing private `--secrets-file` is read as
recovery input and kept intact; new credentials use a new private sibling file.
See [resuming installation](installer-resume.md).

`--secrets-age-recipient age1...` requires `age` on PATH and encrypts each
complete snapshot directly from memory. The directory must be writable only
by its owner. A failed encryption preserves the preceding ciphertext. Decrypt
with `age -d -i /secure/identity install.secrets.age` only outside an agent
transcript. Move the recovery file offline; never display its contents in chat.

`oberth install --verify --json --context selected-context` performs read-only
checks. `--json --yes` also verifies after installing. The version 1 result
contains `ok`, `context`, `server_url`, `mcp_url`, `git_url`, `ca_sha256`
(SHA-256 of DER CA certificate), `first_uplink` when created in this invocation,
and the secrets path and digest when written. `checks` contains stable `code`,
boolean `ok`, and `remedy` for failures.

### Pending forge authorization

When onboarding a forge, `upstream` contains `name`, `url`, `deploy_public_key`,
`fingerprint`, `forge_settings_url`, `state` (`pending` or `verified`), and
`next_command`. The command includes the selected kubeconfig, context, namespace,
and upstream; run it after authorizing the key. Only public key material is
included. `checks` contains `code: "upstream_key_pending"`, `ok: false`, the
`deploy_public_key` inline, and an actionable remedy. If a valid public key is
unavailable, `upstream_public_key` fails and the result remains a real failure.

Exit **0** means every check passed. Exit **3** means the installation is Ready
and only forge-key authorization remains. Exit **1** means an installation or
verification failure; invalid command syntax uses exit **2**. Read JSON even on
nonzero exit. A readiness, TLS, SSH, or other failure takes precedence over exit
3. A pending key is not a reason to reinstall or regenerate the admin identity.

`upstream add --yes --no-wait` persists the upstream and prints its public key
without a forge authentication or repository probe, including when the key
already exists. SSH host-key pins are still validated and persisted. Pending
registration counts for readiness once its SSH identity is available. Forge
acceptance remains a diagnostic, reported by `upstream list --check`.

GitHub deploy keys are per repository: use `/oberth:add-repo` and the specific
repository's **Settings → Deploy keys**, with write access. An organization URL
has no deploy-key page. For organization-wide access, `forge_settings_url` points
to the machine user's SSH-key settings; sign in as that machine user, add the
public key, and grant that account write access to the intended repositories.
Do not attach the install key to the operator's personal account by default.
The result also supplies machine-user settings links for GitLab and Codeberg;
for other forges the field is empty instead of inventing a settings URL.
If no repository exists yet, connect to MCP now and onboard one later.

Tokens and subprocess diagnostics never enter this response. For a remote
install, copy the recovery file through the authenticated SSH channel directly
into the user's chosen secure destination, never into tool output.

## Cluster plan and preflight

Run `oberth install --plan --json --context selected-context` before confirming
installation. The version 1 plan includes `identity.files`, `context`,
`api_server`, `ca_sha256`, `distribution` and node names, architectures,
Kubernetes versions and available filesystem bytes. It reads cluster state;
it does not install prerequisites, create a cluster, write secrets or deploy
anything. `--verify --json` includes the same cluster preflight checks.

An explicit `--kubeconfig` selects one file. Otherwise client-go merges all
files in `KUBECONFIG` (colon-separated on Unix), then uses the default user
kubeconfig when that variable is unset. An explicit context selects that
context in the merged configuration; an unknown name is refused. Several
contexts require a choice. The selected context is also pinned for Helm and
kubectl. Remote and local clusters have the same Review/`--yes` gate.

When no user kubeconfig exists but `/etc/rancher/k3s/k3s.yaml` does, the installer
stops and gives this operator-run command:

```sh
mkdir -p "$HOME/.kube" && chmod 700 "$HOME/.kube" && sudo install -m 600 -o "$(id -u)" -g "$(id -g)" /etc/rancher/k3s/k3s.yaml "$HOME/.kube/config"
```

The original server address stays at `127.0.0.1`. Rerun the plan after copying.
No file is made world-readable. macOS also uses the selected kubeconfig;
clusters must be provisioned by the operator before selecting their kubeconfig.

Preflight fails with a remedy for unavailable prerequisites, unknown cluster
CA, unreadable or unready nodes, unsupported architecture, less than 1 GiB
available node filesystem space and missing default StorageClass. Install also
refuses unknown NetworkPolicy enforcement on fresh installs before making
release changes. Free space comes from the kubelet stats API, not from capacity
or allocatable estimates; unreadable stats fail the check. NetworkPolicy
enforcement is measured with a server Pod and two source Pods per Ready,
schedulable, untainted node in an owned scratch namespace, using the installer's
pinned multi-architecture utility image (or the selected `--utility-image` mirror). The probe checks
allowed traffic, applies default-deny, requires blocked fresh connections,
removes the policy, and requires traffic to recover. It does not infer security
from a CNI/controller name. Plain kind can pass with its own enforcing network.
Unblocked traffic after the convergence window is `absent` and installation is
refused. Pull/RBAC/exec/readiness failures are `unverified` with a remedy; they
never claim enforcement. The probe has a 120-second bound and always attempts
cleanup with its own 30-second bound, including after cancellation. Cleanup
failure names the exact scratch namespace and refuses a successful check.
Plan makes no cluster mutations and reports that enforcement will be checked
first at install, after approval. Install and explicit verification create and
clean up short-lived probe resources. They do not change the selected kubeconfig.

## Upstream name

Review shows the registered name of the first upstream. DNS hosts keep their
first label (`forge.example.test` becomes `forge`). IP literals use their full
canonical address with punctuation replaced by hyphens: `192.0.2.10` becomes
`192-0-2-10`, and `[2001:db8::10]:2222` becomes
`2001-0db8-0000-0000-0000-0000-0000-0010`. IPv6 expansion preserves the
position of zero groups so distinct compressed addresses stay distinct. Ports do not
change the host-derived name. Pass `--upstream-name project-forge` (answers field
`UpstreamName`) before approving the install to choose another valid name.
This controls the first component of repository names, such as
`192-0-2-10/repos/project`; it does not rename existing registrations.
