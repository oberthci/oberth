# v0.19.0 release candidate

This candidate builds on v0.18.1. It makes the MCP endpoint the whole agent
loop (#1514): Oberth records the facts an agent used to poll for as durable
agent events and pushes them to connected MCP sessions, a tool call blocks
until a run finishes or holds, native Argo locks have current and historical
holders, a promotion can prune its source branch once it verified the result
upstream, and `run_get` classifies failures for retry. Everything is generic
Oberth and Argo behaviour, scoped by the caller's uplink. No run status,
label or layout is added. The minor version moves because the MCP surface and
the transport grow.

**MCP tools: 90 → 94.** Added `run_wait`, `events_subscribe`, `events_since`
and `sync_status`, all read-only. `promote` gains `prune_source`;
`branch_delete_many` gains `reason`; `run_get` (full and `summary: true`) and
`run_wait` gain `retry_hint`; `promote_status` gains `prune_source`.

## Server push over MCP

- `initialize` now declares `experimental["claude/channel"]` and
  `resources: {subscribe: true}` and returns an `Mcp-Session-Id`. The POST
  endpoint stays stateless; the session binds only an event filter and run
  resource subscriptions to the bearer credential that opened it. A session
  of another credential answers 404.
- `GET /mcp` (streamable HTTP, `Accept: text/event-stream`) is the session's
  push stream. Each agent event is a `notifications/claude/channel`
  notification (summary plus the event as JSON in `content`, identifier-keyed
  string attributes in `meta`), the notification Claude Code accepts from a
  server declaring the capability; launch it with
  `--dangerously-load-development-channels server:oberth` (or `--channels
  server:oberth` where allowed). `run://<id>` resources support
  `resources/read` and `resources/subscribe`, which sends
  `notifications/resources/updated` for every event about the run.
  `DELETE /mcp` ends a session.
- Event kinds: `run.finished` (status, failed step, reason, retry hint),
  `run.held` (step, pod, `held_since`, `abandon_at`, `holds_in_run`),
  `run.lock_wait` (lock and holders, after `agentEvents.lockWaitThreshold`),
  `promotion.finished` (with the prune outcome), `release.published` and
  `publication.failed` (final, or each automatic retry attempt). Each fact is
  recorded once by key and has a monotonically increasing ID.
- Delivery is at-least-once: SSE event IDs, `Last-Event-ID` resumption, a
  per-session cursor, and `events_since {after_id}` with `gap` when history
  was pruned. Bounds: open streams per credential
  (`agentEvents.maxStreamsPerToken`, 429 beyond), events replayed on connect
  (`agentEvents.maxBacklog`, with a truncation notice naming the cursor), a
  heartbeat (`agentEvents.heartbeat`), per-frame write deadlines that drop a
  slow reader, 16 sessions per credential with one hour idle expiry, and a
  token re-check every 30 seconds.
- Without `events_subscribe` a session receives every kind in its uplink
  scope; `events_subscribe {repos, refs_glob, kinds, own}` narrows it. A
  scoped uplink never receives, reads or subscribes to anything outside its
  upstreams; a hidden repository answers like a missing one.

## Recording

The recorder starts after owner recovery. It reacts to the existing run and
promotion change signals and sweeps every `agentEvents.interval` for parked
holds (the existing hold Pod list, assisted runs only), native lock state
(one Workflow GET per running run, at most 64 per sweep) and publication
retries. It keeps the newest `agentEvents.retention` events and
`agentEvents.syncRetention` lock intervals.

## Tools

- `run_wait {id, until: finished|held|any, timeout_s}` blocks server-side, at
  most 600 seconds, over the same long-poll transport as `wait`, and returns
  `state`, the run summary, unreleased holds and `retry_hint`.
- `sync_status {lock?, since?, limit?}`: current holders and waiters per
  native semaphore or mutex from Workflow `status.synchronization`, and the
  stored history per lock: intervals, `max_concurrent_holders` with when, and
  wait count, maximum, total and median. Sampled at `agentEvents.interval`.
- `promote {prune_source: true}` (single source into the default branch):
  after the promotion passed and the upstream target equals its result SHA,
  Oberth deletes the source branch at the promoted SHA on the mirror and
  queues the upstream deletion, with the same merged check as
  `branch_delete_many`. Any other outcome keeps the branch with the reason.
  A transient upstream read retries for up to an hour. The decision passes
  the audit mutation gate and is audited as
  `promotion.prune_source.pruned|kept`; `promotion.finished` is emitted after
  it.
- `branch_delete_many` (CLI `oberth branch prune --reason`) still refuses
  unmerged branches without `allow_unmerged`, and now refuses to confirm a
  plan with unmerged entries without a `reason`; the reason and the unmerged
  count are in the batch audit.
- `retry_hint {class, cause, action, detail, publication}`: `infrastructure`
  (git transport, eviction, executor identity, image pull, startup deadline,
  a deadline reported below 90% of the budget, interrupted, already
  auto-retried), `code` (step failure, deadline, OOM, storage limit, upstream
  rejection) or `unknown`. While the existing automatic publication retry
  runs (five attempts over about thirty minutes with backoff), `publication`
  shows the attempt and `next_retry_at`.

See [agent events](../agent-events.md).

## Not in this release

The abandoned retry hold reason line (#1514 evidence) ships with the hold
sweep fix in v0.18.2. A `run.hold_abandoned` event follows on top of it.

## Security

- Push carries only what `events_since` returns for the same token: the
  uplink scope is applied when events are read, not when they are written.
- `prune_source` deletes only the exact promoted source branch at the
  promoted SHA, only after verification, through the audited prune path; a
  non-admin promoter can already delete its own branches by push.
- No new Kubernetes permission: the Workflow GET and Pod list already exist.

## Upgrading from 0.18.x

1. **Back up the database first.** Forward migration
   `20261109220004-agent-events-5a27b69187397087ddb6d1f52bd68403` adds the
   tables `agent_events`, `sync_intervals` and `promotion_prunes`.
2. New values under `agentEvents` render as serve flags with the binary
   defaults, so `--reuse-values` upgrades render. The Deployment rolls once.
3. MCP clients that pin the tool list see 94 tools. Clients that ignore
   unknown capabilities and the `Mcp-Session-Id` header are unaffected; the
   POST endpoint still answers headerless, sessionless requests as before.

## Rollback notes

- A v0.18.1 server refuses to open a database with the new migration applied
  (`unknown applied migration ID`). Rolling back means restoring the
  pre-upgrade database backup; a Helm rollback alone does not reverse the
  migration, and the backup discards every run recorded since the upgrade.
- Remove `agentEvents` from the values file before installing the v0.18.1
  chart, whose schema does not know it.
- Pending `prune_source` requests are not executed by v0.18.1; their branches
  stay.
