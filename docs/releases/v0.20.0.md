# v0.20.0 release candidate

This candidate builds on v0.19.0. It makes Argo the single place for run
limits (#1517): how many pipeline Workflows run at once is the Argo
controller's parallelism, the semaphore limits ConfigMap `oberth-sync-limits`
is rendered by the argo-workflows release, and repository concurrency groups
are gone in favour of native Argo mutexes and semaphores. Oberth submits
every admitted run at once. Release serialisation stays an Oberth-injected
native mutex. Everything is generic; no run status, label or layout is added.
The minor version moves because values, flags, tools and a CLI command were
removed and admission semantics changed.

**MCP tools: 94 → 92.** Removed `admission_capacity_config` and
`concurrency_groups`. `sync_status` reports the Argo controller's parallelism
as `Parallelism/workflow-controller`, and `run.lock_wait` covers a postponed
Workflow (`postponed: true`, `running`). No event kind is added: the v0.19.0
schema fixes the stored kinds, and a new kind would need a table rebuild that
a v0.19.0 server could not open. `system_status.admission` drops `capacity`,
`max_runs`, `configuration` and `groups`; run scheduling observations drop
`capacity`, `max_runs` and the `group*` fields; `blocked_by` drops
`run_ceiling` and `capacity`; `status` drops `concurrency_group`, and run rows
drop `ConcurrencyGroup`/`ConcurrencyLimit`. See
[where limits live](../where-limits-live.md).

## The global cap is Argo parallelism

- Oberth's run ceiling is gone: `maxConcurrentJobs`, `--max-concurrent-jobs`,
  `--max-concurrent-jobs-file`, `admission.runtimeCapacity`, the
  `<fullname>-admission` ConfigMap, `admission_capacity_config` and
  `oberth admission capacity`. The admission gate keeps the administrator
  hold, the disk floor and the PSI hard valve, and still orders submission by
  priority then FIFO.
- `oberth install --argo-parallelism N` and `--argo-namespace-parallelism N`
  set `controller.parallelism` / `controller.namespaceParallelism` on the
  managed argo-workflows release (argo-helm 1.0.24, Argo v4.0.8). Unset flags
  keep the release's values. **Default: none**, as Oberth's own default has
  been since v0.18.0 (`maxConcurrentJobs: 0`); a useful number depends on the
  host. The controller reloads its ConfigMap, so a change applies without a
  restart.
- A Workflow Argo postpones is Pending with no `startedAt` and the message
  `Workflow processing has been postponed because too many workflows are already running`
  (verified in Argo v4.0.8 `workflow/controller/controller.go`; the controller
  sets no condition). Oberth recognizes exactly that state:
  - it is exempt from `admission.stallTimeout` and from the pre-start
    watchdog, like a workflow-level lock wait;
  - the reason line reads `waiting for an Argo workflow slot (controller parallelism)`;
  - `sync_status` lists postponed Workflows as waiters and admitted Oberth
    Workflows as holders of `Parallelism/workflow-controller`, with history;
  - `run.lock_wait` is recorded once per wait longer than
    `agentEvents.lockWaitThreshold` with `lock: Parallelism/workflow-controller`,
    `postponed: true`, `waiting_since`, `waited_s` and `running` (Oberth
    Workflows Argo admitted) instead of `holders`.
- What occupies a slot: Argo counts a Workflow from admission to completion,
  so a release waiting for `Mutex/oberth-release`, any Workflow waiting for a
  workflow-level lock, and an assisted retry hold each keep a slot. A
  postponed Workflow holds no lock, so the queue cannot deadlock, but waiting
  releases can delay branch runs; see
  [what occupies a slot](../where-limits-live.md#what-occupies-a-slot).
- Ordering: Argo starts postponed Workflows by `spec.priority`, then creation
  time. Oberth sets no `spec.priority`, so among postponed Workflows the earlier
  submission starts first, whatever its Oberth priority.
- A runtime ceiling an older server stored with `admission_capacity_config`
  stays in the database without effect; startup logs a warning naming it.

## Semaphore limits move to the Argo release

- `oberth install --argo-sync-limit key=N` (repeatable) renders the ConfigMap
  `oberth-sync-limits` in the pipeline namespace through the argo-workflows
  chart's `extraObjects`. The name and namespace are unchanged, so every
  `synchronization.semaphores[].configMapKeyRef` keeps working. The set given
  replaces the previous one; omitting the flag keeps it.
- When the ConfigMap exists from the Oberth chart, the installer hands it over
  first: it annotates the live object for adoption by the argo-workflows
  release and with `helm.sh/resource-policy: keep`, so neither upgrade deletes
  it under running Workflows.
- The Oberth chart refuses non-empty `argoSync.semaphores`, and refuses to
  upgrade while the live `oberth-sync-limits` still belongs to the Oberth
  release without `keep` (a `lookup`; offline `helm template` is unaffected).

## Concurrency groups are gone

- `oberth.ci/concurrency-group` and `oberth.ci/concurrency-limit` are accepted
  and ignored, whatever their value; an invalid name is no longer an admission
  error. The `concurrency_groups` tool, `oberth admission groups` and
  `system_status.admission.groups` are removed; `sync_status` reports native
  lock holders, waiters and history instead.
- The store keeps `runs.concurrency_group`, `runs.concurrency_limit` and
  `concurrency_group_declarations`, unread and unwritten; no migration runs,
  so old data stays readable and a v0.19 server opens the database as is.
- Group membership no longer restricts cancellation: a scoped uplink may
  cancel any branch-trigger run in its scope. Release, tag, apply, promotion
  and scheduled runs stay admin-only.
- A Workflow a v0.19 server submitted with a group annotation is adopted after
  the upgrade; its group no longer holds back new runs.

### Repositories using concurrency groups

Inventory on 2026-11-10 of the `.oberth` directories of the CloudTaser
repositories, of Oberth itself, and of the skipops and terraform repositories:
only **cloudtaser/terraform** declares a group, `terraform-state` (limit 1),
in both `.oberth/build.yaml` and `.oberth/release.yaml`. skipops/terraform,
skipops/terraform-frappe-decom, skipops/terraform-frappe-hr and Oberth's own
`.oberth` declare none. One stale scratch copy of an old cttv tree declares
`kubevirt`; it is not a live repository.

cloudtaser/terraform, both `.oberth/build.yaml` and `.oberth/release.yaml`:

```yaml
# before
metadata:
  annotations:
    oberth.ci/size: M
    oberth.ci/concurrency-group: terraform-state
    oberth.ci/secret-paths: oberth/upstream/cloudtaser/terraform/credentials
spec:
  entrypoint: ci        # release.yaml: release

# after
metadata:
  annotations:
    oberth.ci/size: M
    oberth.ci/secret-paths: oberth/upstream/cloudtaser/terraform/credentials
spec:
  synchronization:
    mutexes:
      - name: terraform-state
  entrypoint: ci        # release.yaml: release
```

Both documents name the same mutex, so a plan never overlaps another plan or
an apply, across branch, promotion and tag runs, as the group did. Update the
comment blocks that describe the group. v0.18 and v0.19 pass `synchronization`
through, so the change can land before the upgrade; during that window the
run is serialized twice, which is harmless. Land it first: after the upgrade
the annotation alone serializes nothing.

## Upgrading from 0.19.x

1. **Back up the database first**, as always. No migration is added.
2. **Land the mutex in repositories that use concurrency groups** (above)
   before upgrading.
3. **Move the semaphore limits** if `argoSync.semaphores` is set:

   ```sh
   oberth install --upgrade --argo-sync-limit kvm=1 --argo-sync-limit heavy-go=2
   ```

   with your current keys. It hands the existing ConfigMap over and renders it
   from the argo-workflows release. Without the installer, follow
   [moving the semaphore limits](../where-limits-live.md#moving-the-semaphore-limits).
4. **Set the Argo parallelism** if you relied on a run ceiling
   (`maxConcurrentJobs` or a runtime `admission_capacity_config` override):
   `oberth install --upgrade --argo-parallelism N`. With no ceiling before, do
   nothing.
5. **Removed Helm values.** Each is still accepted at exactly its former stock
   default, so a `helm upgrade --reuse-values` from a stock 0.19.x install
   renders; any other value fails the upgrade with a message naming the
   replacement. Remove the keys from your values file.

   | Removed value | Removed flag | What to do |
   | --- | --- | --- |
   | `maxConcurrentJobs` (`0` renders; anything else fails) | `--max-concurrent-jobs` | `oberth install --argo-parallelism N` |
   | `admission.runtimeCapacity.{enabled,maxConcurrentJobs}` (`true`, `null`/`0` render) | `--max-concurrent-jobs-file` | as above |
   | `argoSync.semaphores` (empty renders) | none | `oberth install --argo-sync-limit key=N` (step 3) |

   A 0.17.x values file still carries that release's `maxConcurrentJobs: 3`
   and fails; set the Argo parallelism to 3 if you want the old behaviour and
   drop the key.
6. The Deployment loses `--max-concurrent-jobs`, `--max-concurrent-jobs-file`
   and the runtime-capacity volume, so it rolls once. Helm deletes the
   `<fullname>-admission` ConfigMap.
7. MCP clients that pin the tool list see 92 tools. Scripts calling
   `oberth admission groups` or `oberth admission capacity` get a usage error
   naming the replacement.

## Rollback notes

- No migration was added, so a v0.19.0 server opens the database as is. Runs
  started under v0.20.0 have no recorded concurrency group.
- Before installing the v0.19.0 chart, restore `maxConcurrentJobs` if wanted,
  and decide where `oberth-sync-limits` lives: v0.19.0 renders it from
  `argoSync.semaphores` and fails to adopt it while the argo-workflows release
  owns it. Remove it from the argo-workflows release
  (`helm upgrade argo-workflows ... --reuse-values --set-json extraObjects=[]`;
  the object stays because of `keep`), annotate it with
  `meta.helm.sh/release-name=<oberth release>` and
  `meta.helm.sh/release-namespace=<oberth namespace>`, then upgrade.
- v0.19.0 enforces the concurrency-group annotations again; repositories that
  moved to the mutex are then serialized twice, which is harmless.
- The Argo parallelism stays set on the argo-workflows release and keeps
  postponing Workflows; v0.19.0 does not recognize the postponement and its
  startup bound (`admission.stallTimeout`, default 10m) fails a Workflow
  postponed for longer. Clear it (`--argo-parallelism 0`) before rolling back.
