# v0.20.1 release candidate

This candidate builds on v0.20.0. It is a batch of P3 follow-ups from the
reviews of the assisted-continuation sweep (v0.18.2), the MCP agent loop
(v0.19.0) and the retry hold (v0.17.99), plus the RCA's recommended TTL
extension for worked holds. Everything is generic; no run status, label or
layout is added, and no migration.

**MCP tools: 92 → 92.** No tool is added or removed. `run.lock_wait` gains
an optional `hidden_holders` for uplink-scoped readers. The `run_hold_list`
description says how activity extends a hold.

## Assisted holds

- **TTL extension on activity.** A hold with an agent exec, patch or continue
  now ages from its last action instead of `held_since`, so a hold being
  worked is no longer abandoned under the agent at `assist.holdTTL`. Hard
  cap: two hold TTLs after `held_since`, whatever the activity. An idle hold
  is still abandoned at `held_since + holdTTL` (tested). `run.held`
  is recorded once per Pod, so its `abandon_at` stays the idle deadline;
  the server-side deadline moves with each action, up to
  `held_since + 2 × holdTTL`.
- **Held Pod deadline is now step budget + 2 × TTL** (was budget + TTL), and
  the assisted workflow deadline grows by two TTLs (was one), so a hold
  released at the cap still has the step's whole budget for its command. The
  retry expression's budget is derived from the same allowance. Docs, flag
  help, chart text and `AGENT-CONTRACT.md` say so.
- **Victims are re-read before the delete.** The sweep's activity snapshot is
  read before its Pod list, so a continue, exec or patch landing in between
  could be deleted. Each chosen hold's run is now read again right before the
  delete; the hold is spared when the fresh record releases it, extends its
  TTL, or (for the cap) shows activity in the last 5 minutes. An unreadable
  run spares the hold, and the cap moves on to the next idle one.
- **Sweep-only records are not assisted.** A run whose assist record holds
  only server sweep abandons reads `step test failed at attempt 0 (exit 1);
  hold abandoned unserviced after 20m0s (ttl)`, without the `assisted:`
  prefix and the `not evidence` suffix: nobody acted, so its attempt-0
  failure is genuine. With an agent action the clause still joins the
  `assisted: …; not evidence` line.
- **Step name without `OBERTH_STEP`.** A held Pod without `OBERTH_STEP`
  took the raw Argo node name (`wf.ci.test(1)`) as its step, so a sweep
  abandon never matched `FailedStep` and the reason line kept the generic
  deadline prefix. It now uses the failure display's rule: the node's display
  name without the retry suffix.
- **Unreadable assisted verdict.** At finalization of a passed run, a failed
  read of the assisted verdict was logged and treated as assisted, so the run
  finished passed and silently unpublished. The error is now returned and the
  run stays unfinished for the next finalization.

## Agent events

- **`run.held` has its own loop.** The recorder sweep is one goroutine whose
  pending-prune upstream read and Workflow GETs share a budget of up to 30 s,
  so `run.held` could lag by that much. Holds are now observed every 5 s by
  a separate loop beside the sweep (one run list, one Pod list per held run).
  A test with the sweep stuck on a Workflow GET sees `run.held` inside 10 s.
  `agentEvents.interval` no longer paces holds.
- **`run.lock_wait` holders stay in scope.** The recorder stores every
  holder of a lock. For an uplink-scoped reader, `events_since` and the push
  stream now drop holders whose runs are outside its scope from `holders`
  and the summary, and count them in `hidden_holders`; `holder_count` stays
  the total. Unscoped readers see the event unchanged.

## Release runs first in Argo's queues

- Every release run's Workflow carries `spec.priority: 1`; every other run
  carries none (Argo orders it as 0). Argo admits postponed Workflows
  (`workflow/sync/multi_throttler.go`) and grants mutexes and semaphores
  (`semaphore.go`) by priority, then creation time, so a release is no
  longer queued behind branch runs submitted before it (#1517 review P2).
  The trigger decides: documents still cannot set `spec.priority`. It is not
  a Pod priority and preempts nothing.
- The isolation and release-WIF controller proofs were recaptured from the
  authenticated Argo v4.0.8 controller with the retained capture helpers
  (fake clients, no cluster): every captured Pod is unchanged apart from
  timestamps and architecture, and all 24 pass the retained Kubernetes
  v1.35.7 validator.

## Chart and CLI

- `assist.holdTTL` and `assist.execTimeout` take Go durations, as their serve
  flags do: `1h30m` passed the flag but failed the schema
  (`^[0-9]+(s|m|h)$`). `execTimeout` takes the chart's Go duration pattern;
  `holdTTL` takes compound whole-second durations (h, m, s), since the server
  refuses fractional seconds.
- `oberth run hold patch` reads at most 16 MiB (the largest
  `assist.patchMaxBytes`) from `--diff-file` or standard input before
  encoding it, and refuses a larger diff with a usage error. It read the
  input whole before.
- `oberth runs --active` drops the `SIZE` column, which printed `-` for
  every run since v0.18.0.

## Upgrade notes

1. No migration and no new values or flags; existing values files render
   unchanged (any `holdTTL`/`execTimeout` the old schema accepted still
   passes).
2. Holds parked by a v0.20.0 server keep their Pod deadline of budget + TTL
   (Workflows are not rewritten). The new sweep may extend such a hold past
   its TTL; the kubelet then still kills it at budget + TTL from Pod start,
   which can cut the command after a late release short. Service or abandon
   in-flight holds before upgrading, or accept that edge for holds parked
   across the upgrade.
3. Assisted Workflows submitted after the upgrade get the longer held Pod
   and workflow deadlines (two TTLs instead of one). A held run therefore
   keeps its Argo slot and template locks for at most budget + 2 × TTL when
   worked; an idle hold is still abandoned at the TTL.

## Rollback notes

- No migration was added, so a v0.20.0 server opens the database as is.
- Workflows submitted by v0.20.1 keep their budget + 2 × TTL deadlines; a
  v0.20.0 sweep abandons their holds at the TTL regardless of activity.
