# Oberth v0.17.59

This release adds optional Git archive shadow comparisons, step resource
measurements, phase-aware KubeVirt reservations, and administrator-configured
release identities and tag dispatch.
Existing installs need no new values by default. **Back up before upgrading:**
store migration v33 rebuilds `step_results`; rollback requires restoring the
pre-upgrade database as well as rolling back Helm. Follow the
[upgrade and rollback runbook](../upgrade-v0.17.59.md).

## Historical Git experiment (#1205)

This release contained an optional in-process Git comparison experiment.
That implementation, configuration and telemetry have since been removed by
owner decision. The Git CLI is the only supported backend; current runtime
and migration requirements are in [gitcache.md](../gitcache.md).

## Step resource measurements

Supported source-backed container/script steps now report measured usage at
completion. `StepResult` exposes nullable `MaxRSSBytes`, `MemoryPeakBytes`,
`UserCPU` and `SystemCPU`: null/absent means **unknown**, while a measured zero
remains zero. CPU duration values are nanoseconds; divide by 1e9 for seconds.

`MaxRSSBytes` is the Linux waited-process peak RSS, not a sum of simultaneous
processes. `MemoryPeakBytes` reads cgroup v2 `memory.peak`, including page cache;
it is not RSS. CPU counters read cgroup v2 `cpu.stat` for the main container,
including wrapper/executor overhead. Missing or malformed sources stay unknown
independently. Historical zero counters are ambiguous and become null in v33;
positive historical measurements are retained. Unsupported steps, interrupted
wrappers, unavailable final Pod data, and preserved step-written termination
messages can also leave usage unknown.

These are **self-reported advisory counters**: build code can forge its
termination message. They are never used for admission or size grants. No
aggregation is added; future aggregations must saturate on overflow. Consumers
must preserve the distinction between missing measurements and zero.

The wrapper preserves child streams, signals and exit codes, and leaves a
nonempty step-written termination message intact. A command that cannot start
returns 127 (a failed step, rather than executor Error). A signal-killed child
returns 128+signal; killing the wrapper before reporting leaves usage null.

The server executable is seeded once per eligible run (about 51 MB for the
measured Linux/amd64 build). Wrapped Pods get the server binary's architecture
through a strategic-merge `podSpecPatch`; workflow/parent node selectors are
preserved. Mixed-architecture clusters need capacity on that architecture.
No hostPath, extra privileges or additional usage-collection RBAC is introduced.
The [seed benchmark and harness](../step-resource-usage.md#seed-cost-measurement)
measured a local median 0.552 s addition for a 51,576,994-byte executable;
remote storage, API transport and contention can change that cost. Resource and
ContainerSet executors and opaque image entrypoints remain unknown.

Migration **v33 transactionally rebuilds `step_results`** on startup, retaining
its keys, ordering index, diagnostics and log ranges while making counters
nullable and adding cgroup memory peak. It has no down migration. A Helm-only
rollback cannot restore the old schema; restore the pre-upgrade database.

## KubeVirt phase reservations and upgrade safety

Admission reserves the proven peak of live VM demand rather than summing every
VMI template. Only an explicit matching delete that is an ancestor of the later
create separates lifetimes; create completion and `onExit` cleanup do not.
Unknown/unparseable graphs retain the conservative sum. Existing grant values
and defaults are unchanged, and the peak remains reserved for the whole run.
A server-side create guard enforces both workflow and repository limits against
live VMIs and pending claims; launcher Pods cannot create VMIs directly.

**Drain legacy VMI workflows before upgrading.** Workflows without the new
server quota binding are refused at adoption. The chart pre-creates the kept
`oberth-vmi-reservations` ConfigMap in the pipeline namespace; Helm owns only
metadata, and Oberth owns its mutable ledger. **Never use Helm
`--force-replace` or delete the ledger ConfigMap**, including during rollback
or troubleshooting. That discards live/pending reservation state.

After a defunct Workflow is deleted and its resource Pods have disappeared,
dead pending claims are reclaimed on the **next VMI reservation**, once the
five-minute safety margin has elapsed. This is demand-driven reconciliation,
not a background expiry timer. A matching live VMI repairs the claim's UID and
remains charged. A missing claim timestamp starts a fresh grace period.
See the [VMI upgrade note](v0.17.59-kubevirt.md) and
[VM contract](../kubevirt-vms.md#proven-vm-phases-and-the-create-guard).

## Generic release WIF roles and per-step identities

Administrators can define up to 32 `argo.releaseWIF.roles` with DNS-label names
(1–63 lowercase letters/digits/hyphens, no leading/trailing hyphen). Existing
`image-writer`, `image-reader` and `chart-writer` roles retain their behavior.
Every use requires an exact canonical repository + named template -> role
mapping. Unknown, invalid or unmapped roles are refused; provider and cloud
service account remain administrator-pinned. Roles require distinct pools and
target accounts.

Optional `repositories.<repo>.step_service_accounts` maps an approved WIF-only
leaf to a dedicated Kubernetes ServiceAccount, without a dummy secret grant,
Vault role or Vault policy. Each account also requires a `step_routes` pin to
an existing exact route **file and tag pattern**. Copying its template into the
default release file or another route cannot reuse the account, even when two
patterns select the same file. The chart creates these accounts with automatic
token mounting disabled and no RBAC bindings. Only the approved release leaf
receives that identity. Branch, promotion and schedule runs cannot acquire it;
sibling templates and repository/shared/CI/other-step account reuse are refused.
Explicit authored token opt-outs remain vetoes. Existing secret-grant identities
and legacy release mappings remain supported.

No cloud pool, IAM policy or publisher command is changed automatically.
Administrators must provision and verify the exact cloud trust subjects.
See the [configuration example](../upgrade-v0.17.59.md#optional-release-wif-and-tag-routing).

## Administrator-configured release tag routes

`argo.releaseTagRoutes` can route an exact repository's admitted tag glob to a
different `.oberth/<DNS-label>.yaml` workflow. That document declares its own
size, for example `oberth.ci/size: M`; a route has no size override. Default
behavior is unchanged: unmatched tags use `.oberth/release.yaml`; branches,
promotions and schedules use `.oberth/build.yaml`.

Whole-tag path globs support `*`, `?` and character classes; `*` does not cross
`/`. Ambiguous matches are refused, never resolved by list order. Invalid, reserved-contract or
unsafe paths are refused (build, fragment, schedule and tests YAML). Missing/invalid selected workflows fail without
falling back to release.yaml. Fresh default-branch reachability and all release
credential gates still apply. Size, planning, admission, preflight and execution
use the same selected file, recorded as `pipeline_file` in audit evidence.

Routes select files; credential gates still apply. Dedicated WIF step identities
are bound to repository/template plus the exact configured route file and
pattern. Legacy repository WIF role mappings retain their scope; use distinct
template names for distinct capabilities. Configuration changes roll out the server and apply to future or
unsubmitted work and explicit reruns, without rewriting submitted Workflows.
