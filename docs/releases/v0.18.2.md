# v0.18.2 release candidate

This candidate builds on v0.18.1. It is a hotfix for assisted continuation:
the server's hold sweep never saw a hold, so no hold was ever abandoned at
`assist.holdTTL` and `assist.maxConcurrentHolds` was never enforced. Held
runs kept their run slot until the kubelet killed the Pod at step budget plus
TTL, and the run then read as a slow step.

**MCP tools: 90 → 90.** No tool is added or removed. Assist record events
(`run_get` `assist.events[]`, `run_hold_list` `assist`) gain optional
`abandon_reason`, `held_since`, `failed_attempt` and `failed_exit_code` on a
server abandon. No run status, label or layout is added.

## The sweep sees holds again

- **Selector.** The sweep listed Pods labelled `oberth.ci/trigger=branch`;
  `Build` labels branch-CI step Pods `oberth.ci/trigger=ci`
  (`pipeline.TriggerCI`). It now selects with the same constant `Build`
  writes. The unit test built its fixture with the wrong label too; fixtures
  now take their labels from `Build`, and a test asserts the selector matches
  `Build`'s step Pod labels.
- **TTL.** An unreleased hold is abandoned once `held_since` is
  `assist.holdTTL` old, as documented. The kubelet deadline (budget plus TTL)
  is again only the backstop for a server that is down.
- **Log line.** The server logs `assist: hold started run=… step=… pod=…`
  when it first sees a hold, and `assist: abandoned hold run=… reason=…` for
  each abandon.

## Cap rule

- Above `assist.maxConcurrentHolds` the sweep abandons the newest **idle**
  hold first. The sweep runs every 5 s, so a hold that parks over the cap
  fails at once, as if the run were unassisted; holds agents already work
  keep their slots. Before, the newest hold was abandoned regardless, which
  could be the one hold an agent was servicing.
- A hold with an exec, patch or continue in the last 5 minutes is never
  abandoned by the cap. It still counts toward the cap.

## Abandons are recorded

- Every sweep abandon appends a `RunAssistAbandon` event (actor `oberth`) to
  the run's assist record and writes the audit entry `run.assist.abandon`
  with `reason` (`ttl` or `cap`), `step`, `pod`, `held_since` and
  `abandoned_at`. A sweep abandon does not mark the run assisted.
- **Reason line.** A step whose held retry was abandoned reads
  `assisted: step test failed at attempt 0 (exit 1); hold abandoned
  unserviced after 20m0s (ttl); not evidence` in `run_list`, `run_get` and the
  dashboard, instead of `test failed · deadline` with the held Pod's inflated
  deadline. "unserviced" is dropped when the held Pod saw an exec or patch.
  A hold the kubelet killed while the server was down has no record and
  keeps the generic wording.

## Upgrading from 0.18.1

No values, flags or schema change. Roll back to v0.18.1 freely; events
written by this release keep their extra fields and older servers ignore them.
