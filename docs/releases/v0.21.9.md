# v0.21.9

## Promotion and onboarding fixes (#1541)

- Promotions confirm the forge target through the server's configured deploy
  key after publishing. The durable promotion result and `promote_status` expose
  `observed_target_sha`; `promotion.finished` carries it too. A successful push
  alone cannot mark a promotion passed. Failed reads retain bounded retry
  behavior, and historical records remain without an observation.
- MCP schema diagnostics name an unknown or mistyped argument instead of
  returning only “invalid input.” Receive repair documents the exact `action`,
  `repo`, `id` and `reason` arguments and returns actionable validation errors.
- Repository registration accepts a bare slug or a qualified git path matching
  the selected upstream and organization, and rejects mismatched mappings.

The confirmation column requires a forward-only database migration. Restore the
pre-upgrade database backup to roll back the schema.

## Dashboard status and run-list latency (#1540)

Status and MCP system health now read timestamped background forge, Kubernetes
and OpenBao observations. Cold or expired samples no longer make a request wait
for network probes. Run lists refresh startup and queue-demand diagnostics in
bounded background work, retaining current admission reasons and queue order.

A forward-only migration adds indexes for counts, active successors, terminal
pages and typed audit lookups. Grouped lists materialize narrow ref heads once
and apply exact repository/ref predicates before grouping. Existing statuses,
labels, scope rules and pagination semantics are preserved.

The regression fixture includes 50,000 historical runs, 100,000 steps, 2,000 refs,
twenty repositories, four upstreams and sixty active runs. Both handlers and MCP
status must finish in less than 500 ms with blocked diagnostic dependencies.
See [measurement and freshness behavior](../api-latency.md).

## Server CPU and MCP responsiveness (#1540)

- Event readers seek the oldest and newest retained event IDs instead of
  scanning the whole log for each subscriber wake or poll. Lookup cost stays
  nearly constant as retention grows.
- The chart requests 500m CPU for the server and omits its CPU limit by default,
  allowing bursts under queue and event load. The control-plane PriorityClass,
  memory limit and ephemeral-storage limit remain unchanged. Explicit CPU
  overrides remain supported; clear a saved cap with
  `oberth upgrade --set resources.limits.cpu=null`.
- A repeatable load test holds 64 queued runs, 10 running jobs and eight event
  subscribers while asserting MCP response and event-delivery latency.

See [measurements, limitations and reproduction](../server-cpu.md).
