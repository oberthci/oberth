# v0.17.82 candidate integration

This is a historical, unreleased candidate numbering scheme. It is superseded by
[v0.17.84](v0.17.84.md#upgrade-from-v01782-or-v01783): the small v0.17.83 owns
migration 40, and the combined candidate continues at 41–52. Do not use this
historical table to renumber a database or plan a current upgrade.

This candidate integrates token lifetime enforcement, SSH cache recovery,
issue metadata revision checks, publication abandonment, API compatibility
aliases and retired-code cleanup.

Migrations preserve release order: v39 stores submission priority; v40 adds
nullable bearer expiry; v41 adds issue metadata revisions; v42 rebuilds
publications with the terminal
`abandoned` verdict. Existing credentials keep a NULL expiry. New credentials
default to 90 days and are capped at 365 days by server policy.

Restore a verified v38 database backup before running this candidate on any
database previously opened by the discarded experimental issue-workspace
build, whose migration 39 has a different meaning. Startup refuses a database
with `issue_comments`, or recorded migration v40 without
`token_credentials.expires_at`, and directs the operator to a v38 backup.
Priority v39 databases upgrade directly without a restore. Replay-C migrations
follow at v43–v44; replay-D follows at v45–v47. Restore is also required
for rollback; Helm rollback alone cannot undo these migrations.

Before deployment, run the following on a consistent copy of the v38 database
(for example, a verified SQLite backup including committed WAL content):

```sh
sqlite3 /path/to/verified-v38-copy.sqlite 'PRAGMA foreign_key_check;'
```

The check must return no rows. Migration v42 refuses orphaned publications
with an explicit integrity error before rebuilding the table; the migration
transaction rolls back without changing the source rows or recording v39–v42.
Resolve any violations using the original ownership records before retrying,
and preserve the verified v38 backup for recovery.

`GET /api/issues` and `oberth issues --json` return summaries without `Body`,
`ScopeUpstreamID` or `CIWorkSequence`. The authenticated
`GET /api/issues/{id}` route returns full body text under the same upstream
visibility rules as issue lists; the dashboard dialog uses this route. This is
an explicit v0.17.x privacy exception to additive compatibility. See
[API compatibility](../api-compatibility.md).

The public Go import path `pkg/periapsis` is replaced by `pkg/pipeline`.
Downstream Go imports must change. Wire names such as `Burn` and `FailedBurn`
remain stable. Failure attribution chooses the first failed step in declared
order; subsequent cleanup failures remain available as step evidence.

Publication abandonment is audited, never pushes Git objects, and terminates
its owner. The failed owner is projected into the ordinary CI issue history.
Abandoned publications are terminal and cannot be retried. If local promotion
pin cleanup fails after abandonment commits, the response reports success with
a cleanup warning. Repository refresh retries cleanup using the committed
publication state, preserving pins still owned by pending publications.

Authentication failure limits shape responses after authentication: ten failures
per peer/credential and a coarse 100 failures per transport peer each minute.
These limits do not cap backend authentication lookups. Valid credentials from
that peer continue to work, including behind shared ingress.
