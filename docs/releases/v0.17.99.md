# v0.17.99 release candidate

This candidate builds on v0.17.98. It adds agent-assisted CI continuation
(retry hold), off by default; adopts the shared contract guard as a CI leaf
with a recorded debt baseline; and drops a hand-written overflow check in the
step deadline floor.

**MCP tools: 85 → 90.** New tools: `run_hold_list`, `run_hold_exec`,
`run_hold_patch`, `run_continue` and `run_hold_abandon`. `run_rerun` gains
`assist`. New CLI: `oberth run rerun --assist` and
`oberth run hold list|exec|patch|continue|abandon`.

## Agent-assisted CI continuation (retry hold)

A branch CI step fails; instead of a red run, a cold rebuild and a guess, the
run's agent can enter a live copy of the failed step's environment, fix the
files the step reads, re-run the step in place and let the workflow finish
natively. The result is a diagnosis, never a verdict.

- **Opt-in per run.** `git push -o oberth.assist=1` (or `=true`), `run_rerun`
  with `assist: true`, or `oberth run rerun <id> --assist`. The request is
  recorded with the receive reservation like `oberth.priority`, survives
  replay, and becomes the run's immutable `assist_requested`.
- **Honoured only for** branch-tier CI runs started by a branch push or its
  rerun whose workflow declares no secret-store paths, and only while
  `assist.enabled` is on. Release, tag, promotion, schedule, plan and apply
  runs never hold. Otherwise `Build` injects nothing and the run behaves as
  today.
- **Mechanism.** On every eligible leaf (single-main container or script
  template with no authored `retryStrategy`, no credential chain, step
  identity, token mount or nonroot launcher; a document with
  `templateDefaults.retryStrategy` never holds) `Build` adds a server-owned
  `retryStrategy` (`limit: 1`, `OnFailure`, expression
  `asInt(lastRetry.exitCode) > 0 && != 137 && != 143 &&
  asFloat(lastRetry.duration) < <floored step budget>`) and a server-owned
  conditional `podSpecPatch` (`{{= asInt(retries) > 0 ? held : base }}`).
  Attempt 1 runs exactly as today. The retry Pod parks the Argo emissary before
  the step command (`ARGO_DEBUG_PAUSE_BEFORE`), has a Pod deadline of the
  floored step budget plus `assist.holdTTL`, a writable `/work/src`, a
  read-only shared `/work/cache` with its cache variables moved to private
  scratch, and the server's own executable mounted as the Pod helper. The
  Workflow deadline grows by one hold TTL. Only a command that failed on its
  own is retried and held: Argo v4.0.8 records a kubelet `activeDeadlineSeconds`
  kill with the forwarded signal's exit code (143, or 137 after the grace
  period), not `-1`, so signal exit codes and any attempt that ran at least its
  floored budget are refused. #1499 start-up classification and the run-level
  infrastructure retry are unchanged; a timed-out step never gets a second
  budget plus the hold TTL.
- **Tools.** `run_hold_list` (read-only) lists parked attempts with step,
  pod, attempt, `held_since`, kubelet `deadline`, `patch_capable` and
  `released`, plus the run's assist record and the `assist.*` policy.
  `run_hold_exec` runs one argv (no shell) inside the held `main` container,
  bounded by `assist.execTimeout` and `execOutputBytes`, optional `stdin`
  (1 MiB) and `timeout_seconds`. `run_hold_patch` applies a unified diff to
  `/work/src` through the Pod helper `oberth internal-hold-fs`: plain text
  file patches only (no renames, copies, mode changes, binaries, `.git`,
  absolute or parent paths), exact-context hunks, files read and written with
  sha256 preconditions, no symlink following, each file written beside its
  target and renamed into place. `run_continue` creates the release marker so the real command runs
  and the DAG continues. `run_hold_abandon` deletes the held Pod so the step
  fails normally.
- **Authorization and bounds.** Every mutation requires the run's own uplink
  (`run.actor`) or an admin, an active branch CI run that asked for
  assistance, and a run in the caller's scope (the scoped resolution is
  repeated inside the store transaction). Actions are serialized per run and
  capped installation-wide (`assist.maxConcurrentHolds` slots); argv is at
  most 64 entries of 4 KiB. Every action is appended to the run's
  `assist_record` and audited as `run.assist.<kind>` **before** it executes.
  A release that fails abandons the Pod. The hold sweep on the scheduler's
  settlement tick abandons unreleased holds older than `assist.holdTTL` and
  the newest holds above the cap; the Pod deadline is the backstop if the
  server is down.
- **Admission.** Repository YAML may no longer set any `ARGO_*` environment
  name (templates, `templateDefaults` and fragments), so a document cannot
  pause its own attempt 1 or impersonate a hold. `oberth.ci/assist-hold` and
  `podSpecPatch` remain refused from repositories. A hold is recognised only
  on a retry node (`(N)`, N ≥ 1). No RBAC is added: the chart's Argo Role
  already grants `pods/exec` create and `pods` delete in the pipeline
  namespace. Runs placed on remote execution targets are not reachable by the
  hold tools in this release.

### Assisted runs are never evidence

**A run with any `run_hold_exec`, `run_hold_patch` or `run_continue` on a held
step is assisted** (`runs.assisted`, monotonic, set when the action is
recorded, before it runs). An assisted run is excluded from promotion sources
(`greenBranchCandidate`: single promotions, trains and retries), from upstream
publication (the run finishes `passed` in Oberth but `beginRunPublication` is
skipped, so the branch is never force-synced from a tree that is not in Git),
from SHA-pinned fragment evidence (`HasPassedRunForSHA`), and from CI-issue
resolution and issue-trailer closing. A hold continued with no patch and no
exec is still not evidence: nothing in the run proves that nothing touched the
tree. No status, label or layout is added; the existing status carries the
reason line `assisted: step <name> continued after patch sha256:<12 hex> by
<actor>; not evidence` (or `continued after exec`, `continued without
changes`, `patched sha256:…`, `inspected`). A run that asked for assistance
but never held is ordinary evidence. See
[assisted continuation](../assisted-continuation.md).

### Helm values (serve flags; chart default equals binary default)

| Value | Default | Serve flag | Bound |
|---|---|---|---|
| `assist.enabled` | `false` | `--assist-enabled` | |
| `assist.holdTTL` | `20m` | `--assist-hold-ttl` | whole seconds, at most `4h` |
| `assist.maxConcurrentHolds` | `2` | `--assist-max-concurrent-holds` | 1-64 |
| `assist.execTimeout` | `1m` | `--assist-exec-timeout` | at most `15m` |
| `assist.execOutputBytes` | `65536` | `--assist-exec-output-bytes` | at most 4 MiB |
| `assist.patchMaxBytes` | `1048576` | `--assist-patch-max-bytes` | at most 16 MiB; also the largest patched file |
| `assist.patchMaxFiles` | `64` | `--assist-patch-max-files` | at most 1024 |

The feature is **off by default**: `assist.enabled` defaults to `false` in the
chart and the binary. With it off, `Build` injects nothing even for runs that
asked, and every hold tool refuses with "assisted continuation is disabled".

## Contract guard

The shared contract guard runs as the isolated `contract-guard` leaf of the CI
DAG (`.oberth/build.yaml`). `.oberth/contracts/check.py` (with its self-tests
and the generated-files registry) checks the eleven laws listed in the new
TRIZ section of `AGENT-CONTRACT.md`; existing findings are recorded as exact
fingerprints and per-rule counts in `.oberth/contracts/baseline.json`,
re-recorded against this release: the `assist.*` values, `--assist-*` and
`oberth run hold` flags, the two hold annotations, the helper's file-open
suppressions and the growth of functions already over the length limit are
recorded debt until they are registered. The surface registry
(`surface-registry.json`) and deprecation ledger (`deprecations.yaml`) start
empty, so every existing flag, value and annotation is visible debt in the
baseline rather than an approved exception. `.gitea` review and issue templates carry the checklist.
This is a CI gate and documentation only; the server, chart and tools are
unchanged by it.

## Step deadline floor

The floored step deadline is now built with `intstr.Parse`, which keeps the
string form when the value exceeds int32, replacing a hand-written range check
and its G115 lint suppression. No behaviour change; a unit test pins the int, string
and overflow forms.

## Upgrade notes

1. **Back up the database first.** The new migration
   `20261108232919-assisted-runs-2c8c05259f2ff5d590fe8162f2e1d195` adds
   `runs.assist_requested`, `runs.assisted` and `runs.assist_record` with two
   triggers (immutable request, monotonic verdict). It is additive and
   forward-only. Existing migrations are unchanged.
2. **No values change is required.** `assist.enabled` defaults to `false`;
   every other `assist.*` value defaults to the binary default. The Deployment
   gains the seven `--assist-*` serve arguments, so it rolls once.
3. **Admission refuses `ARGO_*` environment names from repository YAML**
   regardless of `assist.enabled`. A repository that sets such a variable in
   a template, `templateDefaults` or a fragment is refused at admission after
   the upgrade until it is removed; the executor's own vocabulary was never
   meant to be set by documents.
4. **With the feature off**, `git push -o oberth.assist=1` and
   `run_rerun assist` are accepted and recorded as `assist_requested` but
   change nothing about the run; the hold tools refuse.
5. **Turning it on** (`assist.enabled: true`) needs no RBAC change and no Argo
   change: holds use the Argo Role's existing `pods/exec` and `pods` delete
   verbs in the pipeline namespace and Argo v4.0.8's emissary pause. Expect an
   assisted run's Workflow deadline to grow by one `assist.holdTTL`, a held run
   to keep its workflow slot, exclusive classes and concurrency group for the
   whole hold, and a held attempt to start with cold caches. Size
   `assist.maxConcurrentHolds` against the workflow ceiling.
6. **Assisted runs are never evidence.** After the upgrade a `passed` run may
   carry the reason line `assisted: … not evidence` and no publication; this
   is by design, not a publishing failure. Push the change as a commit for a
   real green run.
7. MCP clients that pin the tool list see 90 tools.

## Rollback notes

- A v0.17.98 server refuses to open a database with the new migration applied
  (`unknown applied migration ID`). Rolling back means restoring the
  pre-upgrade database backup; a Helm rollback alone does not reverse the
  migration.
- Restoring the backup discards every run recorded since the upgrade, with its
  assist record, assisted verdict and `run.assist.*` audit entries. Do not
  re-create an assisted passed run as evidence by hand.
- Drain assisted runs before rolling back: `run_hold_list` each active
  assisted run and `run_continue` or `run_hold_abandon` its holds, or set
  `assist.enabled: false` and wait for the sweep (`assist.holdTTL`). A
  v0.17.98 server does not know `oberth.ci/assist`, `oberth.ci/assist-hold`,
  the injected `retryStrategy` or the conditional `podSpecPatch`, so adopting
  a Workflow built by v0.17.99 in assist mode can fail its binding check and
  fail the run.
- Remove `assist` from the values file before installing the v0.17.98 chart,
  whose schema does not know it. The v0.17.98 binary does not know the
  `--assist-*` flags.
- v0.17.98 ignores the `oberth.assist` push option and the `assist` argument
  of `run_rerun`; it admits `ARGO_*` environment names from repositories
  again.
- The contract guard leaf and its baseline live in the repository, not in the
  server; a rollback does not affect them.
