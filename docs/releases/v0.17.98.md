# v0.17.98 release candidate

This candidate builds on v0.17.97. It adds runtime administration of release
WIF and workflow capacity, hides archived repositories by default, excludes Pod
start-up from step deadlines, adds administrator-owned exclusive classes, makes
every scheduling and placement setting a Helm value, and finishes the branch
deletion follow-ups from the first production prunes.

**MCP tools: 78 → 84.** New unscoped-admin tools: `release_wif_list`,
`release_wif_grant`, `release_wif_revoke`, `release_wif_reset`,
`admission_capacity_config` (#1497) and `branch_deletion_resolve` (#1500).

## Runtime release WIF and capacity administration (#1497)

- `release_wif_list`, `release_wif_grant`, `release_wif_revoke` and
  `release_wif_reset` (CLI `oberth release-wif`) change release WIF repository
  entries without a Helm upgrade or restart. Helm `argo.releaseWIF` remains the
  boot default and the only source of roles and dedicated step identities. A
  runtime grant binds only existing roles to a registered, unarchived
  repository's own release ServiceAccount; CI identities and another
  repository's release identity are refused. A revoke also removes an entry for
  a retired, unregistered repository. Each admission pins one effective
  snapshot, whose digest joins the spec and audit binding.
- `admission_capacity_config` (CLI `oberth admission capacity <1..64>|clear`)
  sets or clears a server-owned runtime workflow ceiling. Precedence is runtime
  override, then the mounted runtime-capacity file, then the boot flag. The
  override applies immediately and survives restarts and upgrades.
- Overrides live in the server database, never in a Helm-owned object, so
  runtime changes and upgrades cannot conflict. Every change requires a reason
  and is audited with the previous and the effective value.

See [release WIF](../release-wif.md) and
[runtime admission capacity](../runtime-admission-capacity.md).

## Archived repositories hidden by default (#1498)

MCP `repo_list` takes `archived` = `exclude` (default), `include` or `only` and
reports `archived_hidden`. The dashboard runs sidebar, repositories page and
issue repository selector hide archived repositories behind an "archived N"
chip (remembered per browser); a selected archived repository stays visible.
This replaces the v0.17.85 behaviour of listing archived repositories last.
`oberth repos` and `/api/repos` still list every repository.

## Step deadlines exclude Pod start-up (#1499)

Kubernetes counts a step's `activeDeadlineSeconds` from Pod start, so image
pulls, init containers and kubelet contention were charged to the step. Every
literal step deadline is now submitted as `declared + clamp(declared × 50%,
120s, 600s)` (60s → 180s, 300s → 450s, 3600s → 4200s). The declared value stays
the verdict budget and is recorded, with the allowance, in server-owned Pod
annotations (`oberth.ci/step-deadline-seconds`,
`oberth.ci/step-start-allowance-seconds`); repositories cannot set either. The
workflow deadline is unchanged.

A Pod the deadline stops while its main container never started, or before
main used its declared budget, is a `Startup deadline` infrastructure failure:
it gets the existing single automatic retry and is no longer reported as
"Execution deadline exceeded". Steps that used their declared budget,
workflow-deadline kills, image pull errors and OOM kills keep their existing
verdicts. See [workflow deadlines](../workflow-deadlines.md).

## Exclusive classes (#1499)

Administrators can define server-wide classes with a run limit
(`admission.exclusiveClasses`). A step declares `oberth.ci/exclusive: <class>`
on its template metadata, also inside inline templates, `templateDefaults` and
pinned fragments. Membership is per run: at most `limit` runs that declare a
class run at once across every repository and trigger. Further members wait in
Oberth's queue (`exclusive <class> busy`), hold no workflow slot, create no
Workflow or Pod, and never block runs outside the class. A class that is not on
the allowlist refuses the run at admission. Classes are not Argo
synchronization objects, ConfigMaps, node selectors or affinity. See
[exclusive classes](../exclusive-classes.md).

## Scheduling and placement settings are Helm values (#1499)

Every scheduling and placement setting now has a chart value whose default
equals the binary default. New values:

| Value | Default | Serve flag |
|---|---|---|
| `admission.exclusiveClasses` | `{}` (off) | `--admission-exclusive-classes` |
| `admission.stallTimeout` | `10m` | `--admission-stall-timeout` |
| `admission.stepStartupAllowance.enabled` | `true` | |
| `admission.stepStartupAllowance.factorPercent` | `50` | `--admission-step-startup-allowance-percent` |
| `admission.stepStartupAllowance.minSeconds` | `120` | `--admission-step-startup-allowance-min-seconds` |
| `admission.stepStartupAllowance.maxSeconds` | `600` | `--admission-step-startup-allowance-max-seconds` |
| `argo.defaultWorkflowTimeout` | `30m` | `--argo-default-workflow-timeout` (new) |
| `argo.repoWorkflowTimeouts` | `{}` | `--argo-repo-workflow-timeout` |
| `argo.executionTargetConfigMap` | `""` | `--argo-execution-target-config` |
| `argo.executionTargetCredentialsSecret` | `""` | |
| `schedules.minInterval` | `15m` | `--schedule-min-interval` |
| `schedules.maxEntries` | `8` | `--schedule-max-entries` |

`stepStartupAllowance.enabled: false` (or `maxSeconds: 0`) submits step
deadlines exactly as declared. The chart refuses `minSeconds` above
`maxSeconds`. `executionTargetCredentialsSecret` requires
`executionTargetConfigMap`.

## Branch deletion follow-ups (#1500)

- An archived upstream repository no longer undoes a prune. A push the forge
  refuses as archived ("Repo ... is archived", or GitHub's "repository was
  archived so it is read-only") is final after one attempt: the record is
  `skipped` with an "upstream archived" reason line, and the mirror deletion
  and its marker are kept instead of being restored after six retries. Records
  that already failed this way keep their restored mirror branches; prune them
  again to delete them on the mirror only.
- `branch_deletion_list` (and `oberth branch deletions`) `counts` now covers
  every record of the filtered repository, or of all repositories, regardless
  of `--limit`; with `batch` it covers the batch. The new `page_counts` holds
  the counts of the returned page only.
- Failed records can end. They become `skipped` with a reason line, with no
  ref change, when a later deletion of the same branch propagates, when an
  hourly propagator sweep finds the branch gone from the mirror, or through the
  new `branch_deletion_resolve` /
  `oberth branch resolve <repo> --reason <text> [--id <record-id>]...`.
  Without ids it resolves only records whose branch is gone from the mirror
  and lists the rest as `kept`.
- Every `branch_delete_many` plan entry has a `class`: `merged`,
  `patch-equivalent`, `unique` or `unchecked` (beyond the git cherry budget of
  one plan), and `classes` counts every candidate. `report: true`
  (`oberth branch prune --report`, dry run only) also lists the kept candidates
  under `kept`. The plan ID does not change with `report`.
- A feature-branch run whose branch was deleted on the mirror while it was
  publishing finishes `passed` with the reason line "branch ... was deleted on
  the mirror; result not published, upstream left unchanged". Only the
  publication is abandoned; previously the green run was marked failed.

## Upgrade notes

1. **Back up the database first.** The new migration
   `20261108090000-runtime-admin-overrides` (tables `release_wif_overrides` and
   `admission_capacity_override`) is forward-only. Existing migrations are
   unchanged.
2. **No values change is required.** Every new chart value defaults to the
   current behaviour. The Deployment gains explicit serve arguments (stall
   timeout, the three allowance values, the two schedule values and the default
   workflow timeout), so it rolls once.
3. **Exclusive classes are off** until `admission.exclusiveClasses` is set. With
   the default `{}`, any step that declares `oberth.ci/exclusive` is refused at
   admission, so configure the class before a repository adds the annotation.
   Changing the list needs a server restart (a Helm upgrade).
4. **The start-up allowance applies to every step after the upgrade** without
   any setting: a step that overruns its declared deadline is now stopped up to
   `clamp(declared/2, 120s, 600s)` later, and is still judged against the
   declared budget. Pods created before the upgrade carry no deadline
   annotations; until they drain, only the "main exited 0" rule reclassifies
   them. Set `admission.stepStartupAllowance.enabled: false` to keep submitting
   deadlines exactly as declared.
5. **Runtime overrides take precedence over Helm until reset.** After a
   `release_wif_grant`/`release_wif_revoke`, a Helm change to the same
   repository entry in `argo.releaseWIF` has no effect until
   `release_wif_reset`; after `admission_capacity_config`, changes to
   `maxConcurrentJobs` or `admission.runtimeCapacity` have no effect until
   `oberth admission capacity clear`. Check `release_wif_list` and
   `system_status.admission.configuration.source` after the upgrade.
6. A release WIF or capacity change while a release Workflow is in flight
   changes the policy digest an adoption rebuild computes, so a restart during
   that window refuses to adopt the Workflow (fails closed), as a Helm
   `releaseWIF` change does today.
7. MCP clients that pin the tool list see 84 tools.

## Rollback notes

- A v0.17.97 server refuses to open a database with the new migration applied
  (`unknown applied migration ID`). Rolling back means restoring the
  pre-upgrade database backup; a Helm rollback alone does not reverse the
  migration.
- Restoring the backup discards every runtime release WIF and capacity
  override and their audit entries made since the upgrade. Copy any override
  that must survive into `argo.releaseWIF` or `maxConcurrentJobs` /
  `admission.runtimeCapacity` before rolling back.
- Drain running Workflows before rolling back (`admission_hold`, then wait).
  v0.17.97 builds step deadlines without the start-up allowance and does not
  know exclusive classes or the new Pod annotations, so adopting a Workflow
  built by v0.17.98 can fail its binding check and fail the run.
- Remove `admission.exclusiveClasses`, `admission.stallTimeout`,
  `admission.stepStartupAllowance`, `argo.defaultWorkflowTimeout`,
  `argo.repoWorkflowTimeouts`, `argo.executionTargetConfigMap`,
  `argo.executionTargetCredentialsSecret` and `schedules` from the values file
  before installing the v0.17.97 chart, whose schema does not know them.
  Repositories that declare `oberth.ci/exclusive` are refused by v0.17.97
  template-metadata admission until the annotation is removed.
- Branch deletion records resolved as `skipped` stay `skipped`; v0.17.97 reads
  the status and its reason line unchanged.
