# v0.21.0 release candidate

This candidate builds on v0.20.3 and makes `oberth upgrade` the one supported
way to move an installation between versions: it verifies the signed release,
takes a backup, writes a rollback record, and can roll back. Everything is
generic; no run status, label or layout is added, and no migration.

## Signed upgrades

- `oberth upgrade` deploys only a verified signed release. `release.json` and
  the chart are checked against the release key compiled into the CLI; the
  chart digest and the server image digest come from the signed record; any
  failure refuses. `--release-dir` covers hosts without network access,
  `--release-origin` and `--chart-repository` take HTTPS origins.
- Verification covers `oberth upgrade` only. A fresh `oberth install`, a
  same-version `oberth install --upgrade` (for example `--argo-parallelism`),
  and the Helm upgrade a restore applies when compatibility values differ still
  take the chart from the Helm repository unverified; `--image` accepts any
  reference. `--chart` remains the explicit, unverified development override.

## Backup and rollback

- `oberth upgrade` takes a verified history-only backup and writes a rollback
  record before its first change. It refuses to run without a backup unless
  `--no-backup`.
- `oberth upgrade --rollback FILE` rolls back the Helm revisions and, after a
  migration, restores the pre-upgrade backup. It needs `--yes` when it replaces
  the database, and refuses a stale record (either release changed since the
  upgrade) unless `--force-record`, which is labelled dangerous.
- No run of a restored backup is dispatched by itself:
  - onto v0.21.0 and later, running runs whose Workflow is gone become
    interrupted; queued, waiting and mid-submission runs are cancelled with the
    reason "restored from a backup; not dispatched again"; Workflows submitted
    after the backup are deleted;
  - onto an older release, which does not read the restored-runs marker, the
    restore holds admission in the restored database whenever queued or
    running runs exist (allow none, 12 hours), replacing a weaker hold. Check
    the runs, cancel what already ran, then release with
    `oberth admission hold off --reason "restored runs checked"`. A backup
    taken before v0.17.85 cannot carry a hold.
- `--allow-downgrade` accepts an older CLI within one database schema.
- Upgrade and rollback across a schema migration were rehearsed on a throwaway
  cluster, including a rollback to the published v0.20.1
  (`hack/upgrade-e2e/run.sh --rehearse-rollback`,
  `--rehearse-rollback-to-published`).

## Install and upgrade are separate

- `oberth install` and `oberth install --upgrade` no longer change an existing
  release's version, and an older CLI never downgrades the server. Version
  moves go through `oberth upgrade`.
- Changing Argo limits needs no ordered two-release upgrade and causes no
  admission pause: the server follows the controller's digest-named profile
  ConfigMap through a new get-only Role in the pipeline namespace. A plain
  `oberth upgrade` clears the profile pin the v0.20 installer stored. The
  admission pause happens one last time during the upgrade to v0.21.0, because
  the old server still holds the pin.

## Defaults

- `platformProtection.enabled` defaults to `false`, as the documentation
  always said. On an existing release that never set it, the upgrade removes
  the Oberth PriorityClass and prints which classes go; the Argo and OpenBao
  classes are kept. The upgrade refuses if a pod outside the release uses a
  class it would delete. Keep protection with
  `--set platformProtection.enabled=true`.
- `retention.logs.budgetBytes` defaults to 2 GiB on fresh installs. Existing
  releases keep their previous value unless they set one.
- `admission.diskFloorBytes` defaults to 1 GiB everywhere; it only holds new
  runs on a nearly full volume and deletes nothing.
- A fresh Argo install gets controller parallelism of half the allocatable
  CPUs, at least 2. An explicit flag wins and existing releases are unchanged.

## Operations

- `system_status.admin_tokens` (unscoped view) reports the earliest admin
  token expiry and the count expiring within 30 days, with a warning inside 14
  days; the server also logs that warning hourly.

## Upgrade notes

1. Upgrade with the v0.21.0 CLI: `oberth upgrade --yes`. Keep the rollback
   record path it prints.
2. Expect one admission pause during this upgrade (see above).
3. If the installation relied on the old `platformProtection` default, pass
   `--set platformProtection.enabled=true`.

## Rollback notes

- `oberth upgrade --rollback <record> --yes` returns to v0.20.3. v0.20.3 does
  not read the restored-runs marker, so the restore places an admission hold
  when queued or running runs exist; release it after checking them.
