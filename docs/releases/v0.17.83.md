## Workflow deadlines and cleanup

Workflows without an explicit execution deadline receive a 30-minute default,
bounded by repository and server policy. Shorter declared deadlines remain in
effect. Trusted preflight work has a separate deadline starting at admission.
The API and dashboard distinguish that clock from Workflow execution timing.

The server watchdog allows Argo to report its own deadline failure first. It
uses the recorded Workflow start time, or creation time before startup, and
adds the greater of two minutes or ten percent as grace. Completion stops the
watchdog before diagnostic collection. A failed initial API read does not
substitute a shorter default deadline.

Cancellation and preflight expiry release weighted admission while exact-run
cleanup continues. A periodic recovery readback retries terminal preflight
cleanup without requiring a restart. VM capacity remains reserved until
absence is confirmed. Executor-token waiters handle termination signals, and
existing Pods accept only the exact current or supported legacy waiter.

The release workflows retain their 4 CPU / 8Gi ceilings, bounded Go workers
and 4GiB release-test Go memory target. These are declarations and soft runtime
targets; live release-Pod memory and duration measurements remain required.
See [Workflow deadlines](../workflow-deadlines.md) for operational details.
