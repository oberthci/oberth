# KubeVirt phase reservations: upgrade note

Drain all legacy resource-based VMI workflows **before upgrading** the chart
and server. Workflows created before the quota binding was introduced cannot
be adopted by the new server; adoption refuses them with a drain-before-upgrade
hint. Their old resource-create Pods cannot receive new launcher tokens.

New workflows reserve the proven peak of VM lifetimes, with an explicit matching
delete required to separate phases. Unknown graphs keep summed demand. Existing
grant values and defaults are unchanged; this KubeVirt change adds no database
migration. The scheduler
holds the peak for the entire workflow; this does not enable early slot release.

The chart pre-creates the kept public `oberth-vmi-reservations` ConfigMap. Helm
owns metadata only; Oberth initializes and updates the mutable ledger, so an
upgrade or rollback cannot reset its claims. The server gets VMI create/get
and fixed-name ConfigMap get/update; it has no ConfigMap create permission.

Matching live VMIs repair pending claim UIDs after lost responses or failed
completion writes. An abandoned unconfirmed claim is reclaimed after its
resource Pod is gone and a five-minute grace period has elapsed, beyond the
20-second API-create timeout. Recent or still-live operations remain charged.
See [the VM contract](../kubevirt-vms.md) for reconciliation and fail-closed limits.
