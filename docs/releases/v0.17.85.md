# v0.17.85 release candidate

This candidate builds on v0.17.84. It adds durable admission controls, shared
YAML concurrency limits, MCP protocol negotiation, and operator and CI fixes.

## Admission controls

Administrators can hold new admission with a reason, expiry and allowed run
classes. The default allows tags and releases for two hours; promotions can be
allowed explicitly, and an empty allow list holds all new work. Existing grants
continue, expiry survives restart, and the workflow ceiling, pressure, disk and
VM restrictions still apply. The hold is audited and visible through system
status. See [admission holds](../admission-hold.md).

An optional durable branch queue cap limits runs that have not started. The
default is zero (disabled). At capacity, a branch receive keeps its exact SHA
and actor in a durable local backlog and obtains a run later, in receive order.
Tags/releases, promotions and schedules bypass this cap. Deferred branches
remain local until successful CI permits normal upstream publication; they are
not published merely because Git accepted the receive. Configure the cap with
the unscoped administrator tool `queue_cap_config`, and inspect
`system_status.queueCap`. See [queue-cap configuration](../standalone-configuration.md).

Workflow annotations `oberth.ci/concurrency-group` and
`oberth.ci/concurrency-limit` define groups shared across repositories and run
kinds. The limit defaults to one. Conflicting limits fail before execution;
waiting members own no workflow grant or resource reservation. Read definitions,
holders and waiters with `oberth admission groups`, MCP `concurrency_groups`, or
system status. YAML remains the only group-definition surface.

Accepted definitions persist per repository and release mode, including while
idle; they are not keyed by branch or commit. YAML read on another branch can
clear or replace that slot. Existing grants retain their immutable contract.
VM capacity readmission preserves the declared limit, and a conflict with a
retained grant fails only the new run as infrastructure instead of stopping the
scheduler. See [concurrency groups and limit changes](../concurrency-groups.md).

## Operator fixes

- An administrator can pin a waiting run to `normal` or `low`, with an audited
  reason. These explicit lower priorities do not age or regain automatic tag
  urgency. Existing `high` and `highest` rules remain in force, and running work
  is not preempted. See [release priority](../release-priority.md).
- Run status filters consistently distinguish active, failed, superseded and
  infrastructure-retried work. Step-only log selection and promotion lookup by
  a unique short ID work through the remote CLI paths.
- Manual retry reasons remain intact when a later eligible infrastructure
  failure produces an automatic retry. A manual retry starts a fresh request;
  it does not inherit automatic retry lineage. See
  [infrastructure retries](../infrastructure-retries.md).
- Kubernetes capacity waits now report ephemeral-storage and Pod-slot shortages
  as well as CPU and memory. Scheduler regression coverage proves admission
  resumes after disk space recovers. Short run-ID request tests synchronize
  their observations instead of depending on timing.

## MCP compatibility

The endpoint negotiates protocol versions `2025-03-26` and `2025-06-18`, preferring
`2025-06-18`. Initialization requires a valid, nonempty dated `protocolVersion`.
**An initialize request with `params: {}` now returns JSON-RPC `-32602`.**
Unsupported valid dated versions negotiate the preferred supported version;
clients must inspect the response before continuing. Invalid or repeated
version headers are rejected before tool execution. Authentication and tool
scope checks still apply to every call, and existing authenticated direct calls
remain supported. See [MCP protocol behavior](../mcp-protocol.md).

The combined MCP surface contains **80 tools**, including `admission_hold`,
`concurrency_groups` and `queue_cap_config`.

## CI resource declarations

Reviewed CPU, memory and ephemeral-storage measurements now inform the matching
CI and release leaves, with explicit execution deadlines. The merge preserves
the current split test and setup steps, hardened commands, image pins, and
publication structure. Leaves introduced after the resource snapshot retain
their current declarations, except for the split release race groups matched
to their branch equivalents; removed leaves are not restored.
The existing CI policy still caps each CPU request at 1000m. Measurements above
that cap are annotated for remeasurement under the current policy; CPU limits
and reviewed memory/storage values remain explicit. The resource guard is
unchanged and continues to enforce the cap.

Existing larger race deadlines are retained. Against the captured successful
run, the five race/runtime groups have the following headroom:

| Step | Observed execution | Minimum at 1.5x | Deadline |
| --- | ---: | ---: | ---: |
| test-store | 1686s | 2529s | 3960s |
| test-service | 2068s | 3102s | 3600s |
| test-rest | 1573s | 2360s | 3300s |
| test-gitcache | 413s | 620s | 620s |
| test-static-git-runtime | 294s | 441s | 441s |

The latter two deadlines were raised after assembly. Measurements remain
advisory; these repository declarations do not change operator admission policy.
Lint retains its 8Gi memory allocation; store and service race groups retain
their 4Gi memory floors. Git-cache retains the 2000m limit required by its
two-processor race launcher. Split release race groups use the same resources and
deadlines as branch groups. The service Go test timeout is now 60 minutes, so
the inner watchdog also covers the observed duration with at least 1.5x headroom.
Recheck live usage after release, especially leaves whose invocations changed
or whose retained samples were censored. The race-test watchdog comments now
describe the retained whole-group headroom.

## Upgrade from v0.17.84

1. Take a verified database backup before upgrading. Integer migrations stop at
   55. New SQL definitions use immutable timestamp IDs, with the existing
   ledger retaining integer receipts and application times. Candidate receipt
   positions 56–60 are local summaries, not new integer migration identifiers.
   See [schema migrations](../schema-migrations.md).
2. The timestamp migrations introduce the ID ledger, lower-priority overrides,
   admission holds, YAML concurrency declarations and branch queue-cap state.
   Holds and the queue cap default off. Existing data and configured settings
   survive idempotent migration. An older binary must refuse an unknown applied
   timestamp ID; rollback requires restoring the database backup.
3. Audit equal concurrency-group names across repositories before upgrading:
   equal names now intentionally share one limit. Migration seeds definitions
   only from active queued/running grouped runs, not stale terminal history.
   Existing legacy grants are adopted and drain without interruption if their
   combined count exceeds the new shared limit. To change a limit, drain old
   members and clear remembered YAML declarations as documented. Retained grants
   still require ownership-checked cleanup.
4. Update MCP clients that initialize without a valid `protocolVersion`. For
   `2025-06-18`, send the negotiated `MCP-Protocol-Version` header on subsequent
   requests. Check the 80-tool inventory and the scoped/unscoped authorization
   requirements for each new control.
5. After startup, check migration completion, adopted work, group holders,
   admission hold expiry and queue-cap backlog. Enable the optional controls
   deliberately and verify the existing queue reason lines and audited actor.

Local candidate validation does not publish a release or qualify live Kubernetes
placement, production resource headroom, or publication behavior.
