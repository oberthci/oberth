# v0.21.4 release candidate

This candidate builds on v0.21.3. No run status, label, layout or migration
is added.

## Upstreams and forges

- **Breaking:** `upstream add` and `upstream provide-key` no longer take
  `--upstream-key-secret` or `--known-hosts-secret`. The server only ever
  materialized the fixed `oberth-upstream-key` and `oberth-known-hosts`
  bundles, so another name failed with "unknown runtime identity bundle".
- **Multi-key forges.** The upstream authentication probe (used by
  `upstream add`, `upstream list --check` and server readiness) now offers
  only the host-key types pinned for the endpoint, as the Git transport
  already did. A stock OpenSSH forge with RSA, ECDSA and Ed25519 host keys
  pinned through `--expected-host-fingerprint` (which pins only the matching
  key) no longer fails with `knownhosts: key mismatch`.
- **`upstream add --repin`.** Rescans the forge's SSH host keys and replaces
  only this endpoint's pins in the known-hosts bundle, through the same
  audited write and the same trust rules as a first pin (published forge
  fingerprints, `--expected-host-fingerprint`, or an interactive `yes`). Pins
  for other endpoints are kept; a hashed or multi-host entry Oberth did not
  write is refused rather than edited. An identical existing registration is
  kept. A host-key mismatch error now names `--repin`.
- **Organization path check.** `upstream add --check-repo <repo>` reads that
  existing repository through the new upstream (a ref advertisement, no
  objects) before registering it, and `upstream list --check` reads one
  registered repository per SSH upstream. A forge that serves no repository
  at the derived path is reported with the path tried and, for an absolute
  path, the home-relative `ssh://host/~/org` form that plain git-shell forges
  need. The first clone's "does not appear to be a git repository" error now
  carries the same hint.
- **Empty upstreams.** A repository whose upstream default branch does not
  exist yet (an unborn HEAD, which stock OpenSSH forges never advertise) now
  keeps its recorded default branch, `main` for a new cache, even after
  Oberth has synced other branches there. The first promotion or
  default-branch publication creates it. Before, every refresh failed with
  "upstream did not advertise a symbolic default branch", the cache was
  served stale, and runs failed as infrastructure errors and were
  auto-retried. Release tags stay refused until the default branch exists.
  This applies only while the cache has never seen a default branch
  upstream: one that existed and was deleted beside other refs is refused as
  "upstream default branch unknown" rather than read as a new repository, so
  its policy never lapses.
- **Default branch errors are configuration.** An upstream whose HEAD
  resolves without naming its branch still refuses, now as "upstream default
  branch unknown": the run reason says "upstream configuration error", the
  retry hint is `upstream_configuration` (class `code`), and the run is not
  auto-retried.
- **Stale notices say why.** "serving cached repository" now names the
  cause (for example the unknown default branch) instead of always
  "upstream unavailable", and a push's park-policy fallback reports the
  failed refresh's cause instead of "recent upstream policy snapshot
  unavailable".
- **Server SSH host key out of band.** `system_status` and `/api/status`
  carry `ssh_host_key` (the server's public host key) and
  `ssh_host_key_fingerprint`; `oberth status` prints the fingerprint. Both
  arrive over the CA-verified API, so Git clients can pin the push endpoint
  without trusting it on first use.
- **Assisted holds on any image.** The server helper that `run_hold_patch`
  uses is now mounted on every hold-eligible step. It was dropped from steps
  without an explicit memory limit of at least 256Mi (most stock-image
  steps), which made them `patch_capable: false`.
  [Assisted continuation](../assisted-continuation.md) now says exactly when
  a step is patch-capable.
