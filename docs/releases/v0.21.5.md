# v0.21.5

## #1538 — Node reboot failures and safe tag replay

- Retain node boot IDs for owned running step Pods across server resumes. A changed boot ID makes ambiguous kubelet terminations infrastructure failures; branch retries use the existing bounded budget.
- Reboot reason lines name the node and the observed restart window. Missing evidence, ordinary command failures and OOMs keep their existing classification.
- Unknown terminations and exit 255 settle without an assisted hold. Exit 255 reported as a command error additionally requires a resumed step with readable empty output since resume before reboot attribution.
- Skipped publication nodes no longer emit synthetic running progress. Their required timestamps and progress markers do not count as publication execution; earlier starts and publication attempts still require force.
- The chart grants the server only `get` on nodes in a separate role named for its release and namespace, so installations in different namespaces do not collide. Execution targets need the same read permission; no node proxy or kubelet access is used.

## #1527 — Scripted install and verification

- Strict versioned YAML/JSON answers cover the wizard and can be exported at Review.
- Installation requires `--yes`; a local public key can create the first admin before forge onboarding finishes.
- JSON verification reports endpoints, the DER CA pin, identity, and checks with remedies.
- Once-only credentials are saved immediately, with optional age encryption and upstream key recovery copies; save failures fail the install.

Review fixes for #1527: Verify requires the installed Service and a successful forge authentication probe. Credential-store handoff commands decrypt age-encrypted recovery files in a private terminal.

## #1528 — Cluster plan and preflight

- Plan JSON reports the selected kubeconfig files, context, API identity and node facts with actionable preflight checks.
- Multi-file KUBECONFIG preserves the requested context across API, Helm and kubectl calls.
- Fresh k3s requires an operator-owned private kubeconfig copy; root configuration and macOS kind are no longer selected implicitly.
- Verify JSON includes node readiness, free disk, architecture, storage and network-policy checks. Every cluster uses the same Review confirmation.

- Cluster preflight checks controller enforcement settings and node coverage; every install mode refuses untrusted Kubernetes endpoints before API access.

## #1530 — Single-host TLS names and explicit CA replacement

- One-node discovery adds localhost, both loopbacks, node names, `.local`, and node addresses to SANs and Review/plan output.
- Existing CA replacement requires `--reissue-server-ca`; an IP-constrained CA is never replaced by a DNS-only CA.
- Per the owner decision, production CA constraints stay DNS-only and clients connect by `localhost`, the host name or `host.local`, never by IP. CA-level IP constraints are deferred until a released Bun fix and backend support are available. See docs/single-host-tls.md.

- Review fixes keep automatically discovered TLS names tied to the selected node and include them in the machine-readable install result.

## #1529 — Verified plugin bootstrap

- Releases publish checksums for all four CLI binaries and the chart, plus a raw DER ECDSA P-256 signature that OpenSSL can verify with the pinned release public key.
- Publication checks the checksum signature against the authenticated Sigstore bundle and checks every digest against the signed release record.
- The plugin fetches a requested or newest version with curl or wget, OpenSSL, and sha256sum or shasum. Verification failures preserve the existing install.
- `/oberth:install` uses the plugin fetcher. Command tool permissions name only the plugin's own scripts, and CI checks the plugin, release pipeline, and compiled-in CLI key pins together.

- Plugin install uses its bundled wrapper for shared plan/verify checks and
  invokes the verified CLI by its full path, with a required recovery file.


## #1531 — Private unseal and optional TPM2 boot recovery

- `oberth unseal --secrets-file` reads the recovery key privately, decrypts age
  input in memory, submits it on stdin, and prints only seal status.
- The plugin adds `/oberth:unseal`; sealed status and startup hints point to it.
- Explicit single-node host binding writes a TPM2-encrypted systemd credential;
  no plaintext or host-only fallback is retained. TPM reboot qualification
  requires suitable hardware and remains a separate acceptance check.

- Unseal validates the cluster CA and HTTPS before recovery access, rejects a
  failed unsealed-status probe, and uses explicit boot context coordinates.

## #1536 — Mutual TLS for MCP and REST

- A dedicated install client CA verifies certificates, and active uplink SPKI pins bind their authority. Removal, revocation and scope changes take effect on requests and stream revalidation; audit records include the authentication method.
- `uplink cert` and the admin `uplink_cert` tool issue bounded clientAuth certificates from local P-256/Ed25519 CSRs. Installer `--admin-csr` provisions the first admin without a bearer by default.
- Plugin install/connect keep private keys local, merge Claude Code's certificate environment, and register the MCP endpoint only after configuration, without a bearer header in certificate mode.
- Remote commands accept `--client-cert/--client-key`. `client renew` rotates the local pair atomically and enrolls its new pin while the current certificate remains valid. Invite redemption can share `IssueClientCert`.

- Certificate issuance binds the exact active credential, renewal keeps the current identity if a returned certificate is unusable, and explicit bearer setup clears the previous client certificate settings.
