# Oberth v0.17.84 candidate

This candidate builds on the [v0.17.83 candidate](v0.17.83.md), including
its schema-48 migration lineage and shared source/artifact PVC correction.
The chart version is 0.17.84 and its application version is v0.17.84.
Independent CI and live release qualification remain required.

## Credential admission

Uncredentialed branch runs can be admitted while secret reconciliation or
grant loading is unavailable. They receive an empty secret approval set and
do not read secret grants. Release runs, durable credential flags and
credentials found in resolved Workflow documents still require healthy
reconciliation and approved secret access. Inline and pinned fragment
credentials participate in the same classification.

## Peak resource demand and bounded backfill

Admission reports distinguish the concurrent Pod peak, the uncapped total of
known declarations, and the charged resources including server helpers and
headroom. Proven terminal DAG dependencies can reduce the concurrent peak;
ambiguous dependencies remain conservative. The uncapped total is diagnostic.

Once the queue head reaches `max_head_wait_seconds`, new backfill is refused,
even measured EASY work that would finish before the projected head start.
This reverses v0.17.82's measured EASY backfill while draining: existing work
continues, but new work stops passing the head until it can start.

Before that bound, a measured short run may use capacity that is free now
when running durations are unknown, if it finishes within the remaining
head-wait window. If an unknown holder ends early, this new path can delay the
head by up to the remaining window. Unknown holders stay charged; their
capacity is never projected as free.

**Rollback readability:** new timing records can contain `declared_total`.
The strict timing readers in v0.17.83 and earlier reject those records with
`ErrInvalidState: corrupt Workflow timing`, affecting timing display and
`run_get` timing reads after downgrade. Recovery and Workflow adoption are
unaffected. Retaining a readable timing history requires a reader supporting
this field; Helm rollback does not remove it from stored records.

## Upgrade rehearsal

The repository includes a published-to-candidate upgrade harness in
`hack/upgrade-e2e/`. It accepts an explicit published version and ordered
candidate refs, checks migration ledger preservation with target-version
readers, and exercises queue priority admission after each checkpoint.
See its README for execution requirements and the limits of its suspended
Workflow fixture. Inclusion of the harness does not establish a successful
rehearsal for this candidate.

Back up the database before upgrading. Helm rollback does not undo database
migrations. The v0.17.83 capability, namespace audit and retirement
prerequisites continue to apply.
