# Oberth v0.17.84 candidate

This candidate builds on [v0.17.83](v0.17.83.md). Chart version 0.17.84 and
application version v0.17.84 identify this change set. Review the admission
and upgrade sections before rollout.

## Repository context and superseded run reads

Run lists, full run detail and compact `run_get` now include repository, ref,
SHA and admission context. `run_list` and `/api/runs` accept `superseded:true`
to filter before applying the page limit. A branch run is flagged only when
newer queued or running work shares its repository, ref and schedule entry.
Named schedules remain separate from branch pushes and other schedules; tags
and promotion attempts never qualify.

This read-only signal does not cancel work or establish that cancellation is
safe: priority-protected runs and runs with pending publications can still
match. Review the run before an authorized `run_cancel`. Unknown admission
demand remains null, and scoped readers continue to omit global queue
positions. See [run list views](../mcp-setup.md#run-list-views).

## Run list order and queue aging

The run list (`/api/runs`, `run_list`, `oberth runs` and the dashboard) no
longer interleaves queued, running and finished runs by acceptance time. It
lists three groups, top to bottom: the queue, with the run admitted next at
its bottom (the scheduler's own admission order: highest effective class and
earliest queue position closest to the running runs); running runs, most
recently started first; then finished runs, most recently finished first, with
passed and failed interleaved by finish time. The first page always carries
every queued and running run; the page limit counts only finished rows and
older pages continue the finished runs by end time, so no limit or page ever
sorts a queued run below a running or finished one. This also applies to
`latest_per_ref=1`, the dashboard's default view, whose queued and running
heads used to appear among the finished heads. `X-Oberth-Next-Before` and
`next_before` now name the oldest finished run on the page. Migration 50
widens `runs_latest_ref_idx` so ranking every ref's head reads the covering
index only, keeping the grouped page as cheap as the sequence-ordered one.

Queue aging moves a run up one class only. A normal run that has waited 60
minutes becomes effective `high` with the reason `aged: normal run waited at
least 60 minutes`; high work no longer ages into `highest`, so a backed-up
queue cannot turn every run `highest` and erase the manual priority line.
Promotions, the oldest waiting tag release and explicit administrator
`highest` bumps always precede aged work. Within a class the order is FIFO by
admission sequence (the base-class tie-break is gone), and an aged run keeps
its original position, so every high run accepted after it waits behind it:
against high arrivals its wait is bounded by 60 minutes plus the high work
accepted before it. Sustained `highest` arrivals (promotions, tag releases,
admin bumps) can still delay aged and high work without limit, where they
previously shared `highest` FIFO with aged work. `queue_priority_get` still reports
`starvation_minutes: 60`. See [release priority](../release-priority.md).

## Fixed legacy resource charges

Legacy size admission now reserves fixed CPU and memory amounts instead of a
fraction of the numeric budget derived from size weights. Increasing the
budget or changing a weight no longer increases a legacy run's numeric charge.
The size-weight gate and numeric gate both have to fit, including when legacy
and declared runs share capacity.

| Legacy size | CPU charge | Memory charge |
| --- | --- | --- |
| S | 1 CPU | 2Gi |
| M | 2 CPU | 4Gi |
| L | 3 CPU | 8Gi |
| XL | 6 CPU | 16Gi |

These whole-run charges include their safety margin; declared-run executor
and memory headroom additions do not apply. Configure overrides with
`--admission-legacy-resources` or `admission.legacyResources`, using a map such
as `{"L":{"cpu_milli":3000,"memory_bytes":8589934592}}`. Each entry requires
positive CPU millis and memory bytes, bounded by 1000000 millis and 2^50 bytes.
An omitted size keeps its default; if that default exceeds the budget, the run
is refused before waiting, except for exclusive XL.

The chart supplies all four entries explicitly. A configured charge exceeding
the numeric budget fails at startup with an error naming the size and CPU or
memory dimension. Lowering the budget or selecting a positive XL weight can
therefore prevent the upgraded server from starting. Lower the matching
`admission.legacyResources` entries to reviewed values first, or raise the
budget. With `XL=0`, XL remains exclusive and its effective charge is clamped
to the budget in each dimension; a positive XL weight retains the full charge.

Fixed charges can reduce concurrency on smaller budgets. With the default
8 CPU / 16Gi budget, two L runs plus an M fit the weight budget but reserve
20Gi, so the M waits. On larger budgets, fixed charges can instead leave room
for declared work that the old proportional charge held back. Workflows and
their Kubernetes requests and limits are not rewritten.

Admission reservations and blockers expose `legacy_resources` with
`cpu_milli` and `memory_bytes` through `system_status` and per-run `run_get`
admission observations. The dashboard identifies legacy sizing and the fixed
reservation in run details and queued-size tooltips. Claims still preparing
have neither legacy nor declared demand. Size-admitted trusted contract runs
also report legacy charges even when their source contains declarations.
See [declared admission](../declared-admission.md).

## Concurrent demand and resource reports

Admission can now prove ordinary Pod ordering for terminal-state dependency
expressions, including an OR of terminal outcomes for the same predecessor.
Sequential Pods need not all count toward the concurrent reservation. AND
combines proven predecessors; OR retains only predecessors common to every
alternative. Ambiguous expressions, mixed-task OR, negation and early-start
conditions earn no ordering reduction. A mixed-task OR can lose the previous
conditions-assumption notice while retaining conservative demand. Workflow
and template parallelism bounds continue to apply; VM lifetime accounting
keeps its separate rules.

In `run_get` admission observations and `system_status` reservations,
`declared_resources` distinguishes three quantities:

- `declared_total` sums statically expanded Pod invocations, including
  sequential work and static loop iterations before parallelism caps.
- `peak` holds independent upper bounds on concurrent CPU, memory, Pods and
  extended resources, before server allowances.
- The outer `cpu_milli`, `memory_bytes`, `pods` and `extended_resources` hold
  the charged reservation, including executor allowances and memory headroom.

A missing total means unknown, never zero. Dynamic fan-out, analysis bounds,
VM lifetime accounting and older saved demand can leave it absent. Totals are
diagnostic; they do not size admission or change a saved peak. New totals
survive sealed creation and restart adoption, and completed-run timing retains
the raw peak and optional total in `resources.pod_demand`. These are request
envelopes and reservations, not measured usage or a guarantee of Pod overlap.

## Bounded admission backfill

This reverses v0.17.82's measured EASY backfill while draining. At the default
20-minute head-wait limit, new backfill stops, including measured work that
would finish before the predicted head start. Existing grants drain until
the head fits. Setting `--admission-max-head-wait=0` keeps strict FIFO.

Before the limit, candidates are considered in priority/FIFO order and must
fit capacity available now. Measured work can pass the head if its p95 finish
is strictly before the earlier of the predicted head start and the head-wait
deadline. Work in the same effective and base priority classes can also pass
if the head still fits beside it and every surviving grant at the reserved
start. Lower classes cannot use coexistence. Unmeasured candidates can use
only proven coexistence; there is no guessed duration.

There is also a new path when running holders have unknown, retained or
already overrun durations: measured short work may use existing spare capacity
if its predicted finish falls strictly inside the remaining window. Unknown
holders stay charged and are never projected free. If an unknown holder ends
early, a newly backfilled run can delay the head by up to the remaining window
under the forecast. Previously that candidate stayed behind the head. P95
values are not enforced runtime limits; overruns can delay the head further.
Running work is never preempted.

The first head-wait origin remains durable across restarts and priority
displacement. A continuous head's forecast cannot move later; an expired
forecast stops new backfill until the head starts. Changing heads resets the
forecast while retaining the original wait time. The limit ends backfill;
it does not promise admission by that time. Higher-priority work can still
sort ahead, and repository groups, VM capacity, pressure, disk floors and
numeric, weight and run ceilings still apply. See
[priority and fairness](../release-priority.md) and
[admission waits](../ob-admission-wait-report.md).

## Waiting queue survival across restarts

Unadmitted waiting branch, tag, release and promotion runs survive a server
owner restart under their original run IDs, queue and admission sequences,
queued time and priority, including an operator priority override. Recovery
releases the abandoned worker claim, restores queued state and reacquires
admission and credentials. A pending promotion keeps its original CI run
association. A recorded deterministic Workflow name alone does not establish
submission or require Workflow deletion.

This recovery applies to waiting runs without a start time or durable step,
publication or VM execution evidence. An eligible run is retained even beside
a newer active sibling in the same ref and schedule lane; older recovery could
interrupt it. An eligible waiting tag can also be requeued after another run
published that tag. Publication still refuses a duplicate publish, so that
requeued work may run unnecessarily. Admitted work uses its existing adoption,
cancellation and recovery rules. See [restart recovery](../restart-recovery.md).

## Credential admission

Uncredentialed branch runs can proceed without reading secret grants when
secret reconciliation or grant loading is unavailable. They carry an empty
secret approval set. Classification uses the resolved Workflow, including
inline templates and pinned fragments; release runs and durable credential
flags cannot downgrade themselves. Credentialed runs fail closed when
reconciliation is unhealthy or required grant loading fails. Secret approval
requirements continue to apply.

## Trusted policy refresh during upstream outages

Initial admission coalesces concurrent policy refreshes and may reuse a verified
snapshot for up to two seconds. Other policy reads remain fresh. Temporary
transport failures receive up to four attempts with bounded jittered backoff;
failed refreshes never fall back to an earlier policy snapshot. Host-key,
identity, configuration and authorization refusals remain terminal errors.

Runs waiting for a temporarily unavailable trusted policy show the wait cause
and retry within a 30-minute bound. Initial policy waiting precedes resource
admission; a later policy wait can retain an existing reservation. Publication
policy waiting keeps the outbox pending without consuming a push attempt and
releases the delivery permit. Migration 49 persists the first unavailable
publication read, so restart does not reset the wait limit. Successful reads
and terminal publications clear that state. Healthy publications remain
deliverable after extended downtime or ordinary push retry backoff.

## Offline fragment validation

`oberth validate` refuses a document containing unresolved pipeline fragments
and names the references it cannot inspect. The deprecated
`--allow-unresolved-fragments` flag remains accepted but cannot produce a
successful result for unchecked content. Fragment-free documents retain
offline validation. Server-owned fragment resolution, grants and execution
checks still require server validation.

For resolved, fragment-free documents, offline validation and server Workflow
construction now share the document isolation and Trivy checks. A credentialed
CI step using a cache mount, tokenless credential chains and other document-only
refusals therefore fail before submission with the server's diagnostic.
Approvals, grants, ceilings, bound identities and receipts remain server checks.

## Upgrade rehearsal tooling

`hack/upgrade-e2e/` adds a rehearsal harness accepting an explicit published
version and ordered candidate refs. It verifies the signed published inputs,
checks migration ledger preservation with target-version readers, compares
queue identity across upgrades and restarts, and observes priority admission
and Workflow submission after each checkpoint.

The fixture uses suspended Workflows and excludes container execution, normal
completion and publication. It also excludes production TLS, network policy
and secret-store recovery. Inclusion of the harness does not establish a
successful rehearsal of this candidate. See its README for requirements and
the separate migration probe's limits.

If a fixture Pod watch expires after an interrupted wait, the runner performs
a fresh status read and accepts only `Succeeded`. A failed, pending or unreadable
Pod still fails the rehearsal.

## Disposable store test fixtures

Store tests retain file-backed WAL and locking behavior while disabling
power-loss durability for disposable fixtures. Production store opens retain
FULL synchronization. CI bounds the test fixture tmpfs and sizes store race
lanes to 35 minutes from whole-package measurements. Contention tests keep
lookups running alongside writer commits without a throughput timing claim.

## Upgrade from v0.17.83 and earlier

This change set adds migrations 49 and 50 after the inherited schema 48.
Deployments on v0.17.83 apply migrations 49 and 50; deployments skipping that
release apply migrations 40–50 in order:

| Migration | Change |
| --- | --- |
| 40 | Persist bearer token expiry; existing non-expiring tokens remain non-expiring. |
| 41 | Add issue metadata revision and its change trigger. |
| 42 | Add publication abandonment while preserving intent identity and history. |
| 43 | Retain restart Workflow and step timing by attempt. |
| 44 | Guard tag publication identity by repository, tag and result SHA. |
| 45 | Make inactive pilot history read-only; this does not prove external cleanup. |
| 46 | Create the initially empty Workflow capability grant table. |
| 47 | Record the deferred execution-retirement boundary; retain live VM journals, grants, capacity and cancellations. |
| 48 | Copy existing size grants into independent numeric resource ceilings. |
| 49 | Persist the first unavailable publication policy read; clear it on a successful policy read or terminal publication status. |
| 50 | Widen `runs_latest_ref_idx` to cover the run list grouping keys. |

There are no additional flags or settings removed relative to v0.17.83.
When skipping that release, remove its retired `validate --timeout`,
`validate --static`, `init --type`, `install --dev`, `install --production`
and `secretstore materialize` uses; use `secretstore exec` for child execution.
The former `OBERTH_IDENTITY_STORE` / `argo.identityStore` fallback and
`--watch-tunnel-adoption-plan` are also removed. Transfer the previously
chart-managed connector and website publication to external ownership before
applying the chart, including the connector's PriorityClass dependency.
See [identity migration](../identity-migration.md) and
[the v0.17.83 notes](v0.17.83.md).

Retain a verified database backup and its private key before upgrading; see
[backup and restore](../backup-restore.md). Confirm a contiguous migration
ledger and compatible schema. The inherited checks refuse discarded
`issue_comments` layouts, a recorded expiry migration missing
`token_credentials.expires_at`, and orphan publication foreign keys. Follow
the reported repair or compatible-backup restore instructions; do not fill
ledger gaps or renumber migrations manually. The existing capability,
namespace audit and execution cleanup prerequisites still apply. Preserve
the retained VM path's identities, grants and cleanup obligations; schema 47
does not certify resource absence or replace them with capability grants.

Review the fixed legacy charges against numeric budgets before rollout,
especially lowered budgets and shared XL. After upgrade, check startup errors,
readiness, schema 50, queued run identities and priority, admission messages,
adopted Workflows and publication state. Account for the changed backfill order
before relying on increased concurrency.

**Rollback readability:** new timing records can contain `declared_total`.
The strict readers in v0.17.83 and earlier reject such records with
`ErrInvalidState: corrupt Workflow timing`, affecting timing display and
`run_get` timing reads after downgrade. This is separate from schema
compatibility; recovery and Workflow adoption are unaffected. A Helm rollback
neither removes the field nor reverses database migrations. Keep a reader
supporting the field or restore a verified compatible pre-upgrade database
with its matching identity and backup material; prefer forward repair.

CI and live upgrade qualification remain required. Local checks cannot prove
production migration lineage, resource headroom, actual Pod overlap, sustained
queue fairness, identity permissions, network policy, PKI, finalizer cleanup
or publication outcomes.
