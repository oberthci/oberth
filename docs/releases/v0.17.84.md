# Oberth v0.17.84 candidate

This combined candidate builds on v0.17.82 and includes the changes previously
assembled under the unreleased v0.17.83 candidate, plus the v0.17.84 changes.
The separately assembled [v0.17.83](v0.17.83.md) is the smaller run-list order
and status-vocabulary release. Chart version 0.17.84 and application version
v0.17.84 identify this combined change set. Its schema advances from 39 or 40 to 52.
Review admission, DNS and ownership changes and the migration table before rollout.
CI and live upgrade qualification remain required.

## Repository context and superseded run reads

Run lists, full run detail and compact `run_get` now include repository, ref,
SHA and admission context. `run_list` and `/api/runs` accept `superseded:true`
to filter before applying the page limit. A branch run is flagged only when
newer queued or running work shares its repository, ref and schedule entry.
Named schedules remain separate from branch pushes and other schedules; tags
and promotion attempts never qualify.

This read-only signal does not cancel work or establish that cancellation is
safe: priority-protected runs and runs with pending publications can still
match. Review the run before an authorized `run_cancel`. Unknown admission
demand remains null, and scoped readers continue to omit global queue
positions. See [run list views](../mcp-setup.md#run-list-views).

## Issue workspace coordination

Issues now carry a separate work status: `todo`, `active`, `waiting` or
`review`. Existing and new issues default to `todo`. Status updates use the
existing revision, lock and audit rules; only real changes advance the revision.
CI red/green lifecycle behavior remains separate from this coordination state.
Closing and reopening an issue preserves its work status.

Issue lists, compact reads, MCP, CLI and the dashboard expose work status and
computed staleness. Filtering by work status happens before pagination and
counts. Reads do not write stale markers. Open issues become stale after seven
days without an update by default; active issues use a one-hour window. Closed
issues are never stale. Server flags and per-read overrides allow shorter
windows; the active window cannot exceed the general one. When the active
server window is omitted, its default is capped at the configured general
window: setting only `--issue-stale-after=30m` gives both windows 30 minutes.
An explicitly longer active window is refused. Migration 51 adds the constrained
work-status column and extends the metadata revision trigger.
See [issue lifecycle](../issue-lifecycle.md).

## Run list order and queue aging

The run list (`/api/runs`, `run_list`, `oberth runs` and the dashboard) no
longer interleaves queued, running and finished runs by acceptance time. It
lists three groups, top to bottom: the queue, with the run admitted next at
its bottom (the scheduler's own admission order: highest effective class and
earliest queue position closest to the running runs); running runs, most
recently started first; then finished runs, most recently finished first, with
passed and failed interleaved by finish time. The first page always carries
every queued and running run; the page limit counts only finished rows and
older pages continue the finished runs by end time, so no limit or page ever
sorts a queued run below a running or finished one. This also applies to
`latest_per_ref=1`, the dashboard's default view, whose queued and running
heads used to appear among the finished heads. `X-Oberth-Next-Before` and
`next_before` now name the oldest finished run on the page. Migration 40 in the
small v0.17.83 release widens `runs_latest_ref_idx` so ranking every ref's head
reads the covering index only, keeping the grouped page as cheap as the
sequence-ordered one. Migration 52 retains the final candidate's idempotent
rebuild of that same index.

Queue aging is capped at `high`; it never grants `highest`. A normal run that
has waited 60 minutes becomes effective `high` with the reason
`aged: normal run waited at least 60 minutes`; high work no longer ages into `highest`, so a backed-up
queue cannot turn every run `highest` and erase the manual priority line.
Promotions, the oldest waiting tag release and explicit administrator
`highest` bumps always precede aged work. Within a class the order is FIFO by
admission sequence (the base-class tie-break is gone), and an aged run keeps
its original position, so every high run accepted after it waits behind it:
against high arrivals its wait is bounded by 60 minutes plus the high work
accepted before it. Sustained `highest` arrivals (promotions, tag releases,
admin bumps) can still delay aged and high work without limit, where they
previously shared `highest` FIFO with aged work. `queue_priority_get` still reports
`starvation_minutes: 60`. See [release priority](../release-priority.md).

## Fixed legacy resource charges

Legacy size admission now reserves fixed CPU and memory amounts instead of a
fraction of the numeric budget derived from size weights. Increasing the
budget or changing a weight no longer increases a legacy run's numeric charge.
The size-weight gate and numeric gate both have to fit, including when legacy
and declared runs share capacity.

| Legacy size | CPU charge | Memory charge |
| --- | --- | --- |
| S | 1 CPU | 2Gi |
| M | 2 CPU | 4Gi |
| L | 3 CPU | 8Gi |
| XL | 6 CPU | 16Gi |

These whole-run charges include their safety margin; declared-run executor
and memory headroom additions do not apply. Configure overrides with
`--admission-legacy-resources` or `admission.legacyResources`, using a map such
as `{"L":{"cpu_milli":3000,"memory_bytes":8589934592}}`. Each entry requires
positive CPU millis and memory bytes, bounded by 1000000 millis and 2^50 bytes.
An omitted size keeps its default; if that default exceeds the budget, the run
is refused before waiting, except for exclusive XL.

The chart supplies all four entries explicitly. A configured charge exceeding
the numeric budget fails at startup with an error naming the size and CPU or
memory dimension. Lowering the budget or selecting a positive XL weight can
therefore prevent the upgraded server from starting. Lower the matching
`admission.legacyResources` entries to reviewed values first, or raise the
budget. With `XL=0`, XL remains exclusive and its effective charge is clamped
to the budget in each dimension; a positive XL weight retains the full charge.

Fixed charges can reduce concurrency on smaller budgets. With the default
8 CPU / 16Gi budget, two L runs plus an M fit the weight budget but reserve
20Gi, so the M waits. On larger budgets, fixed charges can instead leave room
for declared work that the old proportional charge held back. Workflows and
their Kubernetes requests and limits are not rewritten.

Admission reservations and blockers expose `legacy_resources` with
`cpu_milli` and `memory_bytes` through `system_status` and per-run `run_get`
admission observations. The dashboard identifies legacy sizing and the fixed
reservation in run details and queued-size tooltips. Claims still preparing
have neither legacy nor declared demand. Size-admitted trusted contract runs
also report legacy charges even when their source contains declarations.
See [declared admission](../declared-admission.md).

## Concurrent demand and resource reports

Admission can now prove ordinary Pod ordering for terminal-state dependency
expressions, including an OR of terminal outcomes for the same predecessor.
Sequential Pods need not all count toward the concurrent reservation. AND
combines proven predecessors; OR retains only predecessors common to every
alternative. Ambiguous expressions, mixed-task OR, negation and early-start
conditions earn no ordering reduction. A mixed-task OR can lose the previous
conditions-assumption notice while retaining conservative demand. Workflow
and template parallelism bounds continue to apply; VM lifetime accounting
keeps its separate rules.

In `run_get` admission observations and `system_status` reservations,
`declared_resources` distinguishes three quantities:

- `declared_total` sums statically expanded Pod invocations, including
  sequential work and static loop iterations before parallelism caps.
- `peak` holds independent upper bounds on concurrent CPU, memory, Pods and
  extended resources, before server allowances.
- The outer `cpu_milli`, `memory_bytes`, `pods` and `extended_resources` hold
  the charged reservation, including executor allowances and memory headroom.

A missing total means unknown, never zero. Dynamic fan-out, analysis bounds,
VM lifetime accounting and older saved demand can leave it absent. Totals are
diagnostic; they do not size admission or change a saved peak. New totals
survive sealed creation and restart adoption, and completed-run timing retains
the raw peak and optional total in `resources.pod_demand`. These are request
envelopes and reservations, not measured usage or a guarantee of Pod overlap.

## Bounded admission backfill

This reverses v0.17.82's measured EASY backfill while draining. At the default
20-minute head-wait limit, new backfill stops, including measured work that
would finish before the predicted head start. Existing grants drain for up to
five additional minutes. At 25 minutes with defaults, backfill and claims resume
for work fitting actual available capacity, even without a p95 forecast. The
head remains first at every pass and live reservations stay charged. This can
extend its wait. Setting `--admission-max-head-wait=0` keeps strict FIFO and
disables the escape.

Before the limit, candidates are considered in priority/FIFO order and must
fit capacity available now. Measured work can pass the head if its p95 finish
is strictly before the earlier of the predicted head start and the head-wait
deadline. Work in the same effective and base priority classes can also pass
if the head still fits beside it and every surviving grant at the reserved
start. Lower classes cannot use coexistence. Unmeasured candidates can use
only proven coexistence; there is no guessed duration.

There is also a new path when running holders have unknown, retained or
already overrun durations: measured short work may use existing spare capacity
if its predicted finish falls strictly inside the remaining window. Unknown
holders stay charged and are never projected free. If an unknown holder ends
early, a newly backfilled run can delay the head by up to the remaining window
under the forecast. Previously that candidate stayed behind the head. P95
values are not enforced runtime limits; overruns can delay the head further.
Running work is never preempted.

The first head-wait origin remains durable across restarts and priority
displacement. A continuous head's forecast cannot move later; an expired
forecast stops new backfill until the head starts or the drain cap expires. Changing heads resets the
forecast while retaining the original wait time. The head-wait limit starts the bounded drain;
it does not promise admission by that time. Higher-priority work can still
sort ahead, and repository groups, VM capacity, pressure, disk floors and
numeric, weight and run ceilings still apply. See
[priority and fairness](../release-priority.md) and
[admission waits](../ob-admission-wait-report.md).

## Waiting queue survival across restarts

Unadmitted waiting branch, tag, release and promotion runs survive a server
owner restart under their original run IDs, queue and admission sequences,
queued time and priority, including an operator priority override. Recovery
releases the abandoned worker claim, restores queued state and reacquires
admission and credentials. A pending promotion keeps its original CI run
association. A recorded deterministic Workflow name alone does not establish
submission or require Workflow deletion.

This recovery applies to waiting runs without a start time or durable step,
publication or VM execution evidence. An eligible run is retained even beside
a newer active sibling in the same ref and schedule lane; older recovery could
interrupt it. An eligible waiting tag can also be requeued after another run
published that tag. Publication still refuses a duplicate publish, so that
requeued work may run unnecessarily. Admitted work uses its existing adoption,
cancellation and recovery rules. See [restart recovery](../restart-recovery.md).

## Credential admission

Uncredentialed branch runs can proceed without reading secret grants when
secret reconciliation or grant loading is unavailable. They carry an empty
secret approval set. Classification uses the resolved Workflow, including
inline templates and pinned fragments; release runs and durable credential
flags cannot downgrade themselves. Credentialed runs fail closed when
reconciliation is unhealthy or required grant loading fails. Secret approval
requirements continue to apply.

## Trusted policy refresh during upstream outages

Initial admission coalesces concurrent policy refreshes and may reuse a verified
snapshot for up to two seconds. Other policy reads remain fresh. Temporary
transport failures receive up to four attempts with bounded jittered backoff;
failed refreshes never fall back to an earlier policy snapshot. Host-key,
identity, configuration and authorization refusals remain terminal errors.

Runs waiting for a temporarily unavailable trusted policy show the wait cause
and retry within a 30-minute bound. Initial policy waiting precedes resource
admission; a later policy wait can retain an existing reservation. Publication
policy waiting keeps the outbox pending without consuming a push attempt and
releases the delivery permit. Migration 50 persists the first unavailable
publication read, so restart does not reset the wait limit. Successful reads
and terminal publications clear that state. Healthy publications remain
deliverable after extended downtime or ordinary push retry backoff.

## Offline fragment validation

`oberth validate` refuses a document containing unresolved pipeline fragments
and names the references it cannot inspect. The deprecated
`--allow-unresolved-fragments` flag remains accepted but cannot produce a
successful result for unchecked content. Fragment-free documents retain
offline validation. Server-owned fragment resolution, grants and execution
checks still require server validation.

For resolved, fragment-free documents, offline validation and server Workflow
construction now share the document isolation and Trivy checks. A credentialed
CI step using a cache mount, tokenless credential chains and other document-only
refusals therefore fail before submission with the server's diagnostic.
Approvals, grants, ceilings, bound identities and receipts remain server checks.

## Upgrade rehearsal tooling

`hack/upgrade-e2e/` adds a rehearsal harness accepting an explicit published
version and ordered candidate refs. It verifies the signed published inputs,
checks migration ledger preservation with target-version readers, compares
queue identity across upgrades and restarts, and observes priority admission
and Workflow submission after each checkpoint.

The fixture uses suspended Workflows and excludes container execution, normal
completion and publication. It also excludes production TLS, network policy
and secret-store recovery. Inclusion of the harness does not establish a
successful rehearsal of this candidate. See its README for requirements and
the separate migration probe's limits.

If a fixture Pod watch expires after an interrupted wait, the runner performs
a fresh status read and accepts only `Succeeded`. A failed, pending or unreadable
Pod still fails the rehearsal.

## Disposable store test fixtures

Store tests retain file-backed WAL and locking behavior while disabling
power-loss durability for disposable fixtures. Production store opens retain
FULL synchronization. CI bounds the test fixture tmpfs. Combined-candidate whole-package measurements
size the store race lane and full release package watchdogs to 55 minutes, and
the service race lane to 45 minutes, applying 1.5× observed wall time with
rounding. Contention tests keep lookups running alongside writer commits
without a throughput timing claim. Individual test assertions and contexts
retain their existing bounds; the larger watchdogs detect deadlocks later.

## Bearer token expiry and authentication

New uplink bearer tokens default to 90 days and have a hard maximum of 365 days.
`oberth uplink add --ttl DURATION` selects a positive lifetime within the live
server's policy. Configure lower defaults or maxima with
`uplinkTokens.defaultTTL` / `uplinkTokens.maxTTL`, or serve flags
`--uplink-token-default-ttl` / `--uplink-token-max-ttl`. Issuance reads the policy
from the running daemon and refuses an unavailable policy or excessive TTL
before displaying a token. Expiry applies to bearer authentication; it does
not expire the associated SSH key.

`oberth uplink rotate --ttl DURATION` deliberately sets a new lifetime. Without
that option, rotation keeps the earliest existing absolute expiry, shortened
to the current default lifetime if necessary; an already expired token requires
an explicit TTL. Existing non-expiring tokens retain that status on upgrade;
their replacement receives the default lifetime when rotated. Uplink lists and
the dashboard identify non-expiring tokens, and the server warns at
startup and hourly while active non-expiring credentials remain. Rotate them
with an explicit lifetime. Removal, revocation and replacement checks share the
last-active-unscoped-admin guard and do not count expired bearer credentials
as usable replacements.

Failed HTTP authentication has a ten-failure bucket per transport peer and
credential, plus an independent 100-failure peer ceiling in a one-minute
window. Missing or malformed credentials share an anonymous peer bucket;
forwarded headers do not change the peer. Limited failures return HTTP 429
with `Retry-After: 60`; the dashboard prompts for a token and explains retrying.
Valid credentials behind a shared ingress continue to work. This shapes
failure responses after authentication and does not bound backend credential
lookups. Authentication logs quote fields, for example
`reason="invalid_token"`; update searches that assumed unquoted values.

## Local administration and secret access

The private admin socket moves to `/run/oberth/admin.sock`, in a daemon-owned,
non-symlink directory with mode 0700; the socket has mode 0600. Linux peer
credential checks admit only the daemon UID. The daemon refuses this socket on
other platforms. Update custom launchers, runtime-directory mounts and local
admin integrations that used the old temporary-directory socket. Repository
removal now goes through the live daemon and shares its catalog/cache lock
with Git operations; a mismatched database or cache root is refused.
Repository removal also refuses any legacy KubeVirt grant history, including
revoked grants; archive that repository to preserve its history instead.

Secret-store synchronization removes orphan per-repository and per-step roles
and policies, including roles left after an earlier partial cleanup. Failed
inventories or deletions fail the sync. A degraded repository producer, warning
fallback or unauthoritative desired set refuses destructive synchronization.
Existing per-repository or per-step identities cannot silently fall back to
shared identities when their producer fails or returns an empty set.

Secret grants reject invalid step names and unclean secret-path segments.
Operational repository lookup failures propagate instead of becoming alias
fallbacks. An access revocation whose committed state cannot be confirmed
returns unavailable and directs the operator to inspect `access_list`.
Reserved promotion grants are rechecked before delivery attempts. Scoped
administrators can move issues only to upstreams they can see; moving an issue
to global scope still requires an unscoped administrator.

Runtime identities now always use OpenBao. `OBERTH_IDENTITY_STORE` no longer
selects a Kubernetes Secret fallback, and the obsolete `argo.identityStore`
chart setting is rejected. Readiness no longer accepts identity Secrets as a
substitute for the active identity path. Confirm durable identity persistence,
materialization and workload authentication before upgrading a custom install.
The retained `--upstream-key-secret` and `--known-hosts-secret` flags now name
OpenBao identity bundles. Default key and host files come from
`/run/oberth-identities` rather than projected identity Secret volumes.

## HTTP, MCP and dashboard compatibility

Typed HTTP and MCP records add snake_case aliases alongside existing names;
existing dictionary keys, integer precision and serialized names such as
`JobName`, `Burn` and `FailedBurn` are retained. Run records add `id` and
`run_id`. Run tools accept `run_id` alongside their existing selector; unequal
aliases are refused. Tools advertise plain object input schemas and enforce
required selectors on the server.

HTTP runs, repositories and grants retain their default array responses;
`envelope=1` requests the corresponding MCP object shape. Follow returned
paging cursors, including `X-Oberth-Next-Before`, rather than deriving them from
the last record. CLI run lists use that header, issue lists follow all pages,
and abbreviated run IDs are resolved by the server within caller scope.
`oberth run resources --json` now selects JSON even with `--format=yaml`;
`--json=false` leaves the selected format in effect.

The issue-list privacy exception changes `GET /api/issues` and
`oberth issues --json` to summaries without `Body`, `ScopeUpstreamID` or
`CIWorkSequence`. Read bodies through authenticated `GET /api/issues/{id}` or
`issue_get`; the dashboard fetches those details when an issue is opened.
Issue summaries include their current revision. `GET /api/uplinks` provides
credential status to unscoped administrators without returning tokens.

The owner decision of 2026-11-03 keeps both manual and CI issues in Oberth.
The external-tracker migration and its migration-only export tool are dropped.
Existing writes, scoped visibility and verified database/audit backups remain.
Issue work status and computed staleness are described above. No discussion-thread
model is introduced; append continues to extend the existing body.
See [CI and manual issue scope](../ci-issue-scope.md).

Issue reads expose `revision`, initially 1. `issue_update.expected_revision`
checks metadata atomically; a mismatch is a conflict and omission retains
last-write-wins behavior. Title and body may be updated independently. Only
actual title, state, work-status or scope changes advance it; body edits and locks do not.
`expected_body_sha256` separately checks the body inside the write transaction.
Read the returned revision after a write; see
[issue concurrency and lifecycle](../issue-lifecycle.md).
Dependency failures in issue and scope reads remain errors rather than empty
or missing results. Oversized HTTP/MCP request bodies return HTTP 413 at the
1 MiB bound, and invalid store input is classified as invalid tool input.
Promotion-grant filters distinguish active, revoked, consumed and expired grants.

Legacy API names and default envelopes otherwise remain supported. Future
removals require a later major version, at least 90 days and one stable minor
release after an explicit deprecation announcement. See
[HTTP and MCP compatibility](../api-compatibility.md).

## MCP client and CLI changes

MCP URL precedence is `--url`, `OBERTH_MCP_URL`, then `OBERTH_BASE_URL` with
`/mcp` appended. There is no hosted fallback: without an explicit endpoint,
the CLI refuses before reading a credential file, running a token command or
creating a transport. Load the installer-provided environment or configure the
operator-owned endpoint; older scripts must also supply it.
`OBERTH_TOKEN_COMMAND` is supported when no token is supplied, and
`OBERTH_CA_CERT` supplies the CA unless `--ca-file` overrides it. REST and MCP
validate transport before executing a token command: remote endpoints require
HTTPS, loopback HTTP remains allowed, and MCP refuses HTTPS redirect downgrades.
The same endpoint check covers `oberth mcp call artifact_get --output`: an
unsafe artifact endpoint is refused before credential resolution or transport
creation, and valid downloads honor the configured token command and CA.

Shared CLI parsing accepts flags around positional arguments, preserves `--`
and stdin `-` values, reports missing values as usage errors, and prints help
without treating it as an operation failure. Interrupts exit 130 without a
misleading operational error. MCP tool failures exit 1; usage errors exit 2.
Top-level and admin help now describe the supported commands.

Removed no-op flags are `oberth validate --timeout`, `oberth validate --static`,
`oberth init --type`, `oberth install --dev` and `oberth install --production`.
Remove them from scripts: unknown flags are refused. Init still detects project
markers and emits the generic starter Workflow. `secretstore materialize` is
removed; use `secretstore exec` with declared secret paths and file-based
consumption. Exec requires `--` before its child command. See
[secret delivery](../argo-secret-delivery.md).

Go integrations must update imports from `pkg/periapsis` to `pkg/pipeline` and
use Workflow/stage vocabulary in the renamed Go fields and methods. This is
separate from the retained HTTP/MCP serialized field spellings.
The unused `argoworkflow.NonBlockingTasks` Go helper is removed.
The unused `argoworkflow.ValidateResourceCeiling` and
`argoworkflow.ValidateResourceRequirements` wrappers are also removed. Use
`ValidateResourceCeilingWithCapability` and
`ValidateResourceRequirementsWithCapability`, respectively, passing `nil` for
ordinary resources without a capability grant. These checks still inspect
declarations without changing requests or limits.

## Resource ceilings and admission refusals

Numeric per-container ceilings now have independent administrator authority.
MCP `resource_grant`, `resource_revoke` and `resource_grant_get`, and
`oberth resource grant|get|revoke`, manage Kubernetes quantity strings for
requests and limits. CPU and memory are required in each tier;
ephemeral-storage defaults to 16Gi. Defaults are 4 CPU / 8Gi / 16Gi in both
tiers; global declaration maxima remain 8 CPU / 16Gi / 32Gi. Requests cannot
exceed limits. Grants are audited, repository-scoped, and checked for each
fresh submission, including release work; lookup failures refuse submission.
Archived repositories cannot receive new resource or capability grants.
They validate declarations without inserting requests or limits or resizing
running Workflows.

Migration 49 copies L grants to 4 CPU / 8Gi / 16Gi and XL grants to
8 CPU / 16Gi / 32Gi, preserving actors, timestamps and revocations. Missing or
revoked grants use defaults. Size grants subsequently control only deprecated
size admission and tag-priority policy; changing a size grant cannot overwrite
a custom numeric grant. See [declared resources](../declared-resources.md).

Workflows with partial CPU/memory requests, missing positive effective memory
limits or unbounded declared demand are refused. Complete declarations must
fit the configured host budget including executor and memory-headroom
reserves; oversize work no longer falls back to a size class. The
`--disable-declared-admission` flag and
`admission.declaredResources.disabled: true` refuse new declared work rather
than rerouting it to size admission. Workflows with no CPU/memory requests,
including limits-only Workflows, retain size admission with a deprecation
message directing authors to commit measured declarations. Trusted contract
preflights retain their conservative size reservation. Sizing advice excludes
unfinished attempts. Existing EASY ordering and pressure gates still apply.
Pipeline definitions must contain exactly one YAML document; even an empty or
null second document is refused.

## Workflow capabilities and retained VM execution

The candidate adds `workflow_capability_grant`, `workflow_capability_get` and
`workflow_capability_revoke` for operator-owned, repository-bound resource
access and extended resources. Operators provide the execution-namespace
ServiceAccount, least-privilege RBAC, Argo task-result permissions, TokenRequest
access and ResourceQuota. Grants begin empty; historical KubeVirt grants never
become generic capability authority.

Operator tokens are delivered only to admitted resource executors. Ordinary
container, script and device leaves retain the tokenless pipeline identity,
with service-account token automount disabled; the shared executor retains its
separate account. Recovery and token delivery also refuse the previous
workflow-wide operator identity or mismatched template/executor bindings.
Token cleanup uses persisted resource-executor bindings even after revocation.

The admission interface requires a named resource template with one inline
object and static API version, kind and namespace. Resource templates from
pinned fragments are refused; define them in the consuming repository instead.
Inline templates and template defaults cannot carry resource authority either.
Envelope authorization uses exact-case keys: `apiVersion`, `kind`, `metadata`
and metadata's `namespace`, `name` and `generateName`. ASCII and Unicode case
variants are refused, including variants alongside a correctly spelled key.
Specifications remain opaque and depend on operator RBAC and quota.

Admission also rejects duplicate keys, multiple documents, List objects,
manifest files, arbitrary flags and unsupported dynamic envelopes. Only
`workflow.name`, `workflow.namespace` and `workflow.uid` substitutions are
accepted; adjacent JSON closing braces are not treated as template expressions.
Actions are `create`, `get`, `delete` and `apply`; discovery must identify the
allowed kind as namespaced. Capability Workflows cannot also consume
secret-store or WIF grants or choose shared server/executor/secret identities.

Extended-resource requests and limits must be equal positive integers, and the
bounded graph peak must fit both the grant and explicit server capacity in
`admission.declaredResources.extendedResources` or
`--admission-extended-resources`. There is no implicit device capacity or size
fallback. Revocation blocks new authorization; it does not clean up objects
already created by repository Workflows. See
[Workflow capabilities](../workflow-capabilities.md).

The inactive VM pilot and its node-bridge command are retired; pilot history
is read-only and capacity records remain for investigation. The live VM path
is deprecated but retained: `OBERTH_KVM`, `OBERTH_GUEST_TEST`, guest-test
injection, `.oberth/tests.yaml` release gates, KubeVirt grants and tools,
launcher RBAC, cleanup and recovery still operate. Existing VM chart values
and CLI flags remain active. Stage 2 deletion is deferred; migration 48 neither
freezes nor deletes live journals. The upgrade CLI now requires draining legacy
execution resources before replacement, as described in the upgrade section.

## Deadlines, cancellation and restart recovery

Omitted Workflow deadlines receive a 30-minute server default. Declared shorter
deadlines remain effective; repository caps set with repeatable
`--argo-repo-workflow-timeout upstream/org/repo=20m` cannot raise the global
`--argo-workflow-timeout` ceiling, whose default remains 12 hours. Zero and
negative deadlines are invalid. Administrator timeouts require whole positive
seconds; duplicate repository caps are refused. Local `oberth validate` remains stricter about
an omitted deadline. Trusted preflights use the same policy with a six-hour
hard ceiling and an absolute clock starting at admission.

The server watchdog starts from Workflow creation until Argo reports a start,
then uses that start time. Its grace is max(two minutes, 10% of the execution
budget), allowing Argo to record deadline failures and diagnostics first.
Completed Workflows stop the watchdog before diagnostic collection; restarts
and retries do not reset an adopted Workflow's clock. API and dashboard views
separate preflight, Workflow and watchdog clocks. The executor identity init
container reports its initial wait, progress every 30 seconds and receipt
without printing credentials. See [Workflow deadlines](../workflow-deadlines.md).

Cancelling or timing out a trusted preflight releases weighted admission
promptly. VM capacity remains reserved until ownership-checked cleanup proves
exact-run absence. Accepted deletion requests do not prove finalizers have
finished. A background task retries terminal preflight cleanup every five seconds with
a two-minute attempt budget, freeing capacity after confirmed absence without
a server restart or retrying the run. Owned trusted Workflow spec mismatches
remain run-local failures with cleanup interlocks; foreign identities never
authorize deletion.

## Restart and startup recovery

Restart recovery adopts eligible branch and tag Workflows with their original
run ID. If no resumable Workflow remains and a run has neither step results nor
a publication, recovery can re-queue the original run ID. The durable
cancellation of its prior Workflow must finish before execution resumes;
protected runs retain that identity even beside newer siblings. Logs, original
timing milestones and admission episodes survive; later attempts append
separate timing evidence. Tag publication identity is repository/tag/result
SHA, preventing a replay from creating a second intent for that tuple while
retaining historical records.

Infrastructure-only interrupted promotions may retry automatically, at most
twice, after cleanup and recovery. The original actor must retain authority,
and the original grant must remain valid. Failed CI, manual cancellation,
revocation, expiry and already published work do not authorize automatic retry.
Startup repairs legacy inconsistent publication state only after audit-history
verification. See [restart recovery](../restart-recovery.md).

Transient startup witness, secret-store and Kubernetes dependency failures are
retried with bounded attempts. Startup cancellation cleanup keeps the server
alive and unready, holding dispatch, with two-minute attempts and backoff from
250ms to five seconds. Logs show `recovery_pending=true` / `ready=false` and
readiness reports `scheduler recovery is pending`. Database invariant failures
remain fatal. Terminal checkout-removal failures are deferred to later cleanup
rather than preventing startup; they do not erase durable evidence.

## Publication and Git repairs

Unscoped administrators can use `publication_abandon` or
`oberth publication abandon ID --reason TEXT` to stop a pending publication.
The audited transaction marks the intent abandoned, its run failed/abandoned
and its promotion failed. Idle publication-retry ticks no longer emit an
attempt/outcome log pair when no delivery is due. An in-flight delivery settles
first; earlier ambiguous pushes may already be visible upstream. Abandonment
never undoes a push. Terminal intents are refused and abandoned intents cannot
be retried.
Local promotion pins are released after abandonment; cleanup failure returns
a warning without undoing the abandonment and is retried on repository refresh.
Pending publication pins remain protected, delivered pins are swept, and
legacy pin references migrate to their current names.

SSH Git streams expire after 30 seconds of client transport inactivity;
keepalives and another channel's traffic do not extend that interval. The
idle timer covers Git transport only, so receive finalization and replay use
the existing absolute session bound. Concurrent repository reads can proceed
together while mutations and removal remain serialized. Local filesystem
upstreams are refused by the production Git backend. Module refs and 40/64
character object IDs are validated before Git invocation.

Git output, ref inventories, policy reads and receive outboxes are bounded
while produced; overflow fails instead of accepting a truncated record.
Malformed, oversized, non-regular or invalid receive outboxes quarantine the
affected repository instead of being ignored or followed outside the outbox
root. The original outbox evidence remains in place for operator repair before
further mutation. Abandoned receive quarantine directories are swept during maintenance.
The Go proxy streams module archives through temporary files into immutable
cache objects, verifies cache conflicts, and bounds archive size and transient
backend retries rather than buffering the complete zip in memory.

## Logs, schedules and retained evidence

Retained output now defaults to a per-run 64 MiB ceiling, configurable with
`retention.logs.limitBytes` or `--run-log-limit-bytes`. Exceeding it fails the
run; it is distinct from age and total-storage retention. Dashboard live logs
now surface authentication-error events instead of silently ignoring them.
Failure tails start on complete records, avoiding partial lines and split UTF-8.
Failure diagnosis keeps the first failed step before cleanup, and terminal step
evidence cannot be rewritten by a later observation. Manual log/artifact purges no longer wait
for unrelated automatic sweeps, and sweeps skip already completed candidates.

Cron steps such as `5/15` extend from their starting value to the field maximum;
wildcard-step day fields follow cron day/weekday semantics. Minimum-interval
checks cover month/year boundaries and leap years across the calendar cycle,
so expressions that violate the interval floor are refused even when a short
lookahead would have missed them. Cached interval checks do not hold a global
lock during calendar scans. Status construction retains concurrency-group
information, and audit witness verification counts every verified candidate
even on timeout. Audit timestamping honors the explicit insecure-HTTP option.

## Installer, chart and release changes

Install/upgrade reruns print a server-side Helm preview with sorted changed
value paths and omit values. Release discovery includes pending and failed
revisions; failed reads or malformed responses stop the operation. Repair of a
failed revision compares against the last deployed configuration. Unreadable
live values or a preview without planned configuration refuse apply before
OpenBao or controller changes. Explicit settings reconcile even when versions
already match. Helm and Kubernetes targeting errors propagate.

Reruns preserve service type, network-policy choice, promotion-grant lifetime,
credentialed role, push-banner URL and outstanding witness-genesis
acknowledgements unless explicitly changed. `--network-policy=auto` selects a
default only for a new install; if node discovery cannot identify the cluster,
choose true or false explicitly. New installs default to NodePort. Use
`--push-banner-url=` to clear a banner or
`--install-rekor --accept-witness-genesis=` to clear a consumed acknowledgement.
Generated client instructions use installed Service ports and treat ClusterIP
as internal access requiring an internal route or port-forward. See
[installer reruns](../installer-reruns.md).

## Installer credentials and TLS readiness

Installer child tools do not inherit `BAO_TOKEN` or `VAULT_TOKEN`. OpenBao exec
requires the expected live StatefulSet controller UID. Init failures omit raw
credential-bearing output, while any captured initial credentials are delivered
separately once, including when later setup fails. Deploy-key input must be a
regular file no larger than 1 MiB. Served TLS readiness checks the actual leaf
validity and failed renewal near expiry; metrics expose leaf expiry and renewal
errors. Renewal and probe tasks are cancelled and joined on server exit.

## Chart, connector and release changes

The chart no longer creates the tunnel connector, its configuration,
ServiceAccount, origin-CA object or connector PriorityClass. `watchTunnel`
values are accepted but ignored. Before upgrading an owning release, annotate
all needed live connector resources `helm.sh/resource-policy=keep` and verify
the annotations; see [the handoff procedure](../ownership-handoff.md).
Then move connector ownership to
external manifests, prove replacement Pods can serve traffic, and remove their
reference to the chart's connector PriorityClass or provision an external one.
The bundled website and its release/publish pipeline are removed; arrange an
external owner before relying on that publication path. The connector adoption
flag `--watch-tunnel-adoption-plan` and its recovery tooling are removed.

Explicit empty `argo.ciSecrets.serviceAccount` and `argo.ciSecrets.vaultRole`
strings now select their defaults for this release with deprecation. Before
the next chart release, omit those overrides or set the default names explicitly.
The retired boolean `argo.enabled` remains accepted for reused values. Release
WIF credential validation binds fixed roles to allowed pools while allowing
operator-selected provider names. Build gates add Helm, Python and production
deadcode checks. Release leaves retain 4 CPU / 8Gi limits, bounded Go processes
and serialized packages; the release-test Go soft memory target is 4GiB.
Resource requests are unchanged; actual duration and memory peaks need CI.

The integrated production deadcode gate drops stale allowlist entries for
removed components and moves test-only helpers out of production. Remaining
retained VM protocol helpers have explicit, narrowly scoped exceptions pending
their staged removal. Git reader concurrency tests now use shared fixture
budgets instead of fixed latency bounds; production Git behavior is unchanged.

The v0.17.82 release already contains the single run-PVC volume
layout and the 1-or-2-byte secret refusal. They remain in this candidate.
Source and artifact subPaths share one volume; source, CA and binary inputs
remain read-only. Existing persisted Workflows are not rewritten. Secret exec
still refuses a child when a fetched value is 1 or 2 bytes after removing
trailing newlines; move short non-secret settings out of secret paths.

## Upgrade impact

This is the preparatory release for legacy execution retirement. Existing
VM/KVM/guest execution, grants, revocation, cleanup, capacity protection and
restart recovery remain enabled. `oberth admin retirement-check` provides an
explicit, read-only migration check; it does not run at server startup. Final
execution removal requires a later published release after dependent pipelines
have migrated and their drain, cleanup and backup receipts are accepted.

Before upgrading from a chart that owns the connector or site resources, transfer
those resources to an external owner and retain the required ownership proof.
Apply the documented keep annotations before a Helm upgrade can prune them.
Preserve external PriorityClasses and resource requests/limits. The optional
Argo/OpenBao priority examples change priority only; they supply no installation
resource sizing. See the ownership handoff, platform protection and retirement
upgrade procedures.

NetworkPolicy behavior changes on upgrade, including when using stored Helm
values that omit the new keys. UDP and TCP DNS egress on port 53 now targets
resolver Pods in `networkPolicy.dnsNamespace`, defaulting to `kube-system`.
Set that value to the resolver namespace. For host-networked or node-local
resolvers not represented by ordinary Pods in that namespace, explicitly set
`networkPolicy.dnsAnyDestination=true` before upgrade; this permits DNS to any
destination. Without the appropriate setting, pipeline DNS can stop working.

Pipeline ingress allows pipeline peers and this release's server Pod only;
both server namespace and identity labels must match. Set
`networkPolicy.pipelineIngress.enabled=false` only when wider listener access is
intended. `networkPolicy.enabled=false` disables both directions. Fresh k3s
installs keep NetworkPolicy enabled, while reruns preserve an existing operator
choice and report when enforcement is disabled. An enforcing CNI remains
required; unrelated policies may grant additional traffic.

Installation checks both namespaces for incompatible Pod Security enforcement
before writing. New namespaces receive the privileged enforcement label needed
by the supported execution modes; existing baseline/restricted policy is not
weakened automatically. The server Role no longer inherits wildcard core-resource
authority. For a legacy Argo Role rules ownership conflict, follow the explicit
ownership migration procedure; the utility preserves rules and requires a
reviewed dry run and compare-and-swap application. Existing PVC list/update
permissions have active callers and remain required.

Issues remain in Oberth. The migration-only issue exporter and external-tracker
workflow are removed. Existing scoped issue reads and writes, revision/body-hash
conflict checks, and verified database/audit backups remain. The final candidate
adds issue work status and computed staleness as described above; append still
extends the issue body rather than creating a discussion thread.

The small v0.17.83 release owns migration 40; the final candidate changes
now occupy 41–52. This branch adds no migration beyond them. The next new
branch-specific migration is 53. Follow the migration table and backup/restore
requirements below.

Mutation-gate verification retries bounded timeouts under I/O pressure, with a
fresh per-attempt budget and a finite overall deadline. Expiry preserves earlier
contention evidence, while corruption and cancellation keep their refusal rules.
Release helper checksums have been rebuilt reproducibly for the pinned Go
1.26.10 Linux/amd64 build, restoring CI and publication pin verification.

Initial workload Pod placement and each workload Pod's executor identity startup
are separately bounded to ten
minutes using durable Kubernetes creation times. A timeout reports its reason
through existing failure messages, and admission is released only after a
terminal result or successful cleanup. The executor-identity lifetime Pod stays
deliberately gated and is not execution progress. At the configured head-wait limit, new backfill stops. Admission draining is capped
at five additional minutes after the configured head wait; available-capacity
backfill then resumes without discarding live reservations. With defaults this
occurs after 25 minutes of head wait. Strict FIFO mode remains strict. See the
admission wait documentation for the fairness tradeoff and cleanup behavior.

## Upgrade from v0.17.82 or v0.17.83

The combined schema has exactly one migration at each version 1–52. The small
v0.17.83 release owns migration 40 (the run-list covering index). The former
final-candidate migrations 40–51 move to 41–52. This branch adds no migration
beyond that sequence; new branch-specific migrations start at 53.

A schema-39 v0.17.82 database applies 40–52. A schema-40 small v0.17.83 database
keeps its recorded index migration and applies 41–52. Both upgrade paths preserve
existing ledger timestamps, data and audit history. A v40 database with bearer
expiry from the old unreleased candidate numbering is incompatible and is
refused with backup recovery guidance. Do not renumber an existing ledger or
insert placeholder entries to make it match.

| Migration | Change |
| --- | --- |
| 40 | Small v0.17.83: covering run-list order index, without bearer expiry. |
| 41 | Persist bearer token expiry; existing non-expiring tokens remain non-expiring. |
| 42 | Add issue metadata revision and its change trigger. |
| 43 | Add publication abandonment while preserving intent identity and history. |
| 44 | Retain restart Workflow and step timing by attempt. |
| 45 | Guard tag publication identity by repository, tag and result SHA. |

Before upgrading from v0.17.82 or the small v0.17.83 release, remove retired `validate --timeout`,
`validate --static`, `init --type`, `install --dev`, `install --production`
and `secretstore materialize` uses; use `secretstore exec` for child execution.
The former `OBERTH_IDENTITY_STORE` / `argo.identityStore` fallback and
`--watch-tunnel-adoption-plan` are also removed. Transfer the previously
chart-managed connector and website publication to external ownership before
applying the chart, including the connector's PriorityClass dependency.
See [identity migration](../identity-migration.md) and the retained execution
upgrade procedure below.

Retain a verified database backup and its private key before upgrading; see
[backup and restore](../backup-restore.md). Confirm a contiguous migration
ledger and compatible schema. The inherited checks refuse discarded
`issue_comments` layouts, a recorded expiry migration missing
`token_credentials.expires_at`, and orphan publication foreign keys. Follow
the reported repair or compatible-backup restore instructions; do not fill
ledger gaps or renumber migrations manually. The existing capability,
namespace audit and execution cleanup prerequisites still apply. Preserve
the retained VM path's identities, grants and cleanup obligations; schema 48
does not certify resource absence or replace them with capability grants.

Review the fixed legacy charges against numeric budgets before rollout,
especially lowered budgets and shared XL. After upgrade, check startup errors,
readiness, schema 52, queued run identities and priority, admission messages,
adopted Workflows and publication state. Account for the changed backfill order
before relying on increased concurrency.

**Rollback readability:** new timing records can contain `declared_total`.
Older strict readers without support for this field reject such records with
`ErrInvalidState: corrupt Workflow timing`, affecting timing display and
`run_get` timing reads after downgrade. This is separate from schema
compatibility; recovery and Workflow adoption are unaffected. A Helm rollback
neither removes the field nor reverses database migrations. Keep a reader
supporting the field or restore a verified compatible pre-upgrade database
with its matching identity and backup material; prefer forward repair.

`oberth upgrade` now refuses while legacy execution resources remain. It checks
Workflows in the installed pipeline namespace for
`oberth.ci/trusted-kvm-intent`, and VMs and VMIs across namespaces for
`oberth.ci/tier=vm-runner`, `oberth.ci/vm-spec` or `oberth.ci/vm-identity`.
Unrelated objects do not block it. Discovery, permission, decoding or inventory
failures refuse the upgrade; an absent API group is distinguished from an
unreadable advertised resource. The operator's Kubernetes access needs
discovery and list permissions; this adds no server/chart RBAC.

The check covers `--dry-run`, ordinary upgrades, same-version repairs and
explicit same-version value changes; a true no-op skips it. Neither `--yes`
nor `--wait-idle` bypasses it. Completed or terminating resources still block
until the API confirms absence. Inventories run before preparation and again
after preview/drain, before the first live write. These two observations are
not a durable admission pause. Direct Helm/image replacement bypasses the CLI
guard and must follow the same drain and absence checks.
Completed preflight Workflows remain for `argo.workflowTTL` (default 3600 seconds,
or 1 hour); wait for TTL collection or deletion by the current server. A delayed
TTL controller can extend that wait.

The inactive VM pilot is retired; the live KVM preflight and VM execution path
are retained. Complete these steps before replacing the running owner:

1. Before upgrading, inventory `vm_suite_executions` and `vm_suite_resources`
   on a database copy and match any outstanding external objects to their
   recorded owner. Resolve remaining cleanup obligations through that verified
   owner; migration 46 makes these histories read-only and does not confirm
   cleanup or release their capacity reservations. Preserve the history and
   ownership evidence for investigation; the removed node-bridge and pilot
   components cannot resume it after upgrade.
2. For repositories using the retained path, preserve `vm.kvm.enabled`,
   `trustedTests.recipes` and the explicit positive
   `trustedTests.kvmSupplementalGroup`. Check the KVM device plugin, approved
   recipes and pinned images, execution-namespace RBAC, and existing KubeVirt
   grants against the installed configuration. Inventory `OBERTH_KVM`,
   `OBERTH_GUEST_TEST`, guest-test injection and `.oberth/tests.yaml` gates;
   they still run in this candidate. Do not remove their prerequisites on the
   assumption that generic capabilities replace them automatically.
3. Record live `vm_executions`, `vm_capacity_slots`, `kubevirt_grants` and
   pending cancellations, with the corresponding Workflow and external-object
   identities. Keep the existing server and controller running. Stop new legacy
   submissions at their sources, including pushes, release requests and
   scheduled triggers, then finish or cancel existing legacy runs through the
   current server. Preserve their grants and cleanup RBAC until confirmed
   resource absence. Do not delete journals or clear capacity to force
   readiness: deletion acceptance is not proof of exact-run absence, and the
   recovering owner needs these records. Restore failed controllers, API access
   or cleanup permissions for stuck finalizers; orphan cleanup requires separate
   review of the exact object name, UID and owner. Retry
   `oberth upgrade --dry-run` after resources disappear, then upgrade while new
   legacy submissions remain stopped. Schema 48 preserves the recovery engine;
   it does not waive this upgrade check. See the
   [retirement upgrade procedure](../retirement-upgrade.md).
4. If planning a later capability migration, provision the operator-owned
   ServiceAccount, least-privilege RBAC, TokenRequest access, quota and explicit
   device capacity. Grant the repository separately, move guest and suite
   gates into its Workflow, and prove cleanup before removing any deprecated
   execution dependency. The included security fixes do not certify an
   installation's capability migration; qualify its identity and cleanup paths
   separately.
5. After upgrading, inspect adopted or recovered work and outstanding cleanup.
   Persistent `recovery_pending=true` / `ready=false` requires checking
   Kubernetes API access and cleanup permissions. Confirm exact-run absence
   and released capacity before treating cleanup as complete; a successful
   schema migration or an accepted delete request is insufficient. Check that
   required guest and suite gates still block publication when they fail, then
   resume submissions.

CI and live upgrade qualification remain required. Local checks cannot prove
production migration lineage, resource headroom, actual Pod overlap, sustained
queue fairness, identity permissions, network policy, PKI, finalizer cleanup
or publication outcomes.

## Automatic infrastructure retries

Eligible branch infrastructure and workflow-level failures now receive one fresh
attempt automatically, preserving their original queue position and priority.
Test/step failures, cancellations, promotion/plan/apply/release-tag runs and an
already retried lineage are excluded. Cleanup, current admission and atomic audit
checks remain enforced. The existing message line records the source and cause;
no run status or layout is added.

Helm `autoRetryInfrastructure` defaults to true, including upgrades with the value
absent. Set it to false (server `--auto-retry-infrastructure=false`) for manual-only
recovery. One retry is a fixed cap. This change adds no migration; legacy retry
lineage remains readable and terminal history is not replayed. See
[the administrator and upgrade guide](../infrastructure-retries.md).
