# Oberth v0.17.81

## Admission by measured memory requests

Memory admission now reserves the concurrent sum of container memory requests,
plus executor allowances and max(1Gi, 10% of declared run memory) headroom.
Kubernetes continues to enforce container limits and schedule pods by requests.

Before relying on increased concurrency, review existing memory requests that
were never measured. A low request paired with a high limit now reserves less
capacity. Containers without complete requests or positive memory limits retain
legacy size admission. No workflow resources are rewritten.

Administrators can configure the fixed minimum and proportional component using
`--admission-memory-headroom-bytes` and `--admission-memory-headroom-percent`, or
`admission.declaredResources.memoryHeadroomBytes` and
`admission.declaredResources.memoryHeadroomPercent` in the chart. Unset settings
use defaults; explicit zero disables that component. Both components must be
zero to disable headroom. Existing IO/run ceilings and host protections remain.

The memory admission change itself requires no database migration. See
[declared resources](../declared-resources.md) for accounting and upgrade details.

Oberth's build and release workflows declare measured memory requests and
reviewed limits, so their reservations use this request-based accounting.

## Host pressure admission

- Host pressure admission uses CPU/IO some avg10 defaults of 30%/20%, hard
  starvation limits of 50%/40%, and a 30-second settle window between grants
  unless CPU is below 15% and IO below 10%. Starvation starts at the first
  pressure deferral and permits one grant per pass and settle window.
- Upgrade note: enabled host pressure admission enforces even when reused values
  explicitly set legacy `admission.pressure.mode: observe`. The server logs a
  startup warning for this setting. Set `admission.pressure.enabled: false` for
  budget-only admission. See [host pressure admission](../native-scheduling.md).

## Priority builds and grants

- Upgrade applies schema migration 39, adding `priority_grants` and
  `run_priority_requests` and supersession protection for existing queued or
  running high/highest runs. Migrations are forward-only: Helm rollback does
  not undo migration 39. Retain a verified pre-upgrade database backup and its
  private key; reverting the schema requires restoring that backup. See
  [backup and restore](../backup-restore.md).
- Priority builds can be requested through Git push options and MCP. Unscoped
  administrators can grant an identity `high` or `highest` priority until an
  expiry, list grants, or revoke them for future submissions. Accepted builds
  retain their priority after grant expiry or revocation.
- Submission priority only raises a run's automatic class. Promotions and eligible
  oldest tags retain `highest`, RC patterns retain `high`, and refused/invalid
  requests appear separately in `priority_refusal`. Priority requester ownership
  never grants admin cancellation rights for tag, release, promotion or
  concurrency-group work.
- Queue order uses effective class, then base class, then original FIFO order.
  Explicit `highest` precedes aged normal work when capacity frees. Aging alone
  cannot guarantee a time bound under a continuous stream of base-highest work.
- Protected priority and RC runs survive ordinary supersession. Every matching
  RC push queues and runs independently. `oberth.supersede=true` is honoured on
  priority pushes, but replacing protected work requires its requester or an
  unscoped admin; branch, schedule-entry, promotion and publication guards apply.
- `schedule_trigger force` bypasses busy/paused checks and replaces only
  unprotected same-branch, same-entry work for a normal-priority submission.
  Protected work remains; priority schedule submissions queue independently.
- For this release, every backfill behind a high/highest head is refused. Normal
  heads keep bounded backfill. This guard remains until the EASY backfill release.
- Trusted preflight recovery and eligible automatic infrastructure retry retain
  protected work's own admission place alongside newer normal pushes. Recovery
  cannot supersede those siblings, and existing retry/evidence guards remain.

- Oversized tags and tags whose size-limit lookup fails retain any accepted
  submission priority after an admin override, before falling back to normal.
  Admission messages behind high/highest heads state that every later run waits.

See [release priority and fairness](../release-priority.md) for queue semantics
and administrator controls.
