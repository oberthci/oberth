ISSUE 001: Offer an existing cluster or kind creation instead of a red missing-kubeconfig error

Status: Open
Reported: 2026-10-04
Affected version: Oberth v0.17.9 (6f40126bc8f6), macOS

Priority: Medium
Evidence: User report, installation screenshot, and reproduced in the live setup test.

Problem
Docker Desktop, kind, and Helm are installed, and Docker is available. There
is no configured Kubernetes cluster yet. This is a valid starting point for
creating a kind cluster, but oberth setup presents this red warning:

  cluster detection: build REST config: invalid configuration: no configuration has been provided, try setting KUBERNETES_MASTER environment variable

This makes a supported first-run state look like a prerequisite failure and
points users at a low-level environment variable instead of the available
setup choices. The same wizard successfully created a kind cluster afterward.

Reproduction
1. Use a machine with Docker Desktop running, kind and Helm available, and no
   usable/default kubeconfig. Use an isolated test environment; do not remove
   a real kubeconfig just to reproduce this issue.
2. Run oberth setup with the interactive UI.
3. Observe the red cluster-detection error on the welcome screen.
4. Continue and select Create kind cluster; setup is able to proceed.

Expected behavior / requested copy
Use a neutral onboarding prompt, for example:

  No Kubernetes cluster configured.
  Provide a kubeconfig path for an existing cluster, or create a new one with kind.

Offer clear actions:
  - Use an existing cluster: choose/provide a kubeconfig path and context.
  - Create a local kind cluster using Docker Desktop.

The kubeconfig-path action is a requested UX improvement, not a claim that
v0.17.9 already offers that control. Keep the choice available in plain and
accessible mode as well; see issue 011.

Acceptance criteria
- Missing kubeconfig is an informational state when local kind creation is
  available; no red REST-config error or KUBERNETES_MASTER suggestion appears.
- Docker daemon availability and kind/Helm installation are checked separately
  from whether an existing Kubernetes cluster is configured.
- Selecting kind continues without first requiring a kubeconfig.
- Selecting an existing cluster allows a kubeconfig path and context to be
  validated before installation targets that cluster.
- Malformed explicitly selected kubeconfigs, unreachable selected clusters,
  unavailable Docker, and missing dependencies still produce specific,
  actionable diagnostics. Do not suppress genuine configuration failures.
